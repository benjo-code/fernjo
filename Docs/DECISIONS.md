## 2026-11-16 – M5 restore semantics and backup container
**Context:** Milestone 5 adds import, export and restore (`Docs/superpowers/specs/2026-11-16-m05-import-export-design.md`; file formats in `Docs/backup-format.md`). The rules for what a restore does to existing data, how a half-applied state is avoided and which container the backup uses are not obvious from the code.
**Decision:** **Replace vs merge:** a full backup (`.fjbk`) **replaces** the tree and all vault entries after a confirmation that names what is lost; the master password and data key stay; the `.bak` files are kept and afterwards hold the pre-restore state. The connections-only JSON and the mRemoteNG import **merge** into a new top-level folder with fresh ids (`Imported from fernjo export (date)`, `Imported from mRemoteNG (date)`; a second one on the same day gets " (2)", " (3)"). A vault that exists must be unlocked even for a backup without entries (replacing it then empties the vault); without a vault file a backup with entries asks for a vault first (`vault_needed`); an unreadable vault is never overwritten (`vault_unusable`). The restore never creates a vault and never reuses the backup password as a master password. **Plan, then apply:** `fernjo-import` does no I/O on app data; it returns a plan (folder with fresh ids, vault entries under the ids the tree references, report) or the decrypted backup. The decrypted plan waits in one pending slot in Rust (`AppState.pending`, `Pending` in `src-tauri/src/import_commands.rs`), so secrets never reach the webview; a new pick replaces it, a successful apply, cancel and every main-window page load clear it. A wrong key or password keeps the picked file so the UI can ask again. **Order and rollback:** import adds all entries with ONE vault save (`Vault::add_entries_with_ids`: ids and names are validated first, so a refused batch changes nothing), then `Store::graft`; if the graft fails, the entries are removed again with one more save (`Vault::remove_entries`). Restore closes all sessions, snapshots the current entries, runs `Vault::replace_entries`, then `Store::replace_tree`; if the tree step fails the snapshot is put back. When the rollback itself fails the errors are distinct and say what state is left: `import_incomplete` (N imported entries could not be removed, remove them in the vault) and `restore_incomplete` (the vault may hold the backup's entries while the tree is the old one; the previous vault content may still be in `vault.fernjo.bak`, unless the failed rollback save got as far as replacing it, so the message says "may"). **Vault `.bak` after an import:** the entries are added with one save, so `vault.fernjo.bak` holds the vault as it was before the import (and, as after a restore, the state from before it). After a rolled-back import the rollback is a second save, so the `.bak` then holds the vault with the imported entries still in it. (Until 2026-11-17 the import saved once per entry, which left N−1 entries in the `.bak`, cost O(N²) bytes and did the rollback with N more saves; see "M5 final review fixes".) **Backup container:** an own format `FJBK` (magic `FERNJOBK`, version 1) built on `fernjo_vault::seal_with_password` / `open_with_password` (Argon2id with the vault's default cost, XChaCha20-Poly1305, the whole header as associated data, KDF parameters bounded like the vault's load bounds, password NFC-normalised), body is versioned JSON. The export password is separate from the master password, at least 8 characters, never stored; a wrong password cannot be told from a damaged file (`wrong_password`). **Dates:** folder names use the local date (`chrono::Local`, `today_local`), timestamps inside files are UTC RFC 3339 with `Z`. **Debug-only dialog override:** the native pick and save dialogs run in Rust (the webview never passes a path); in debug builds only, `FERNJO_DIALOG_FILE` replaces both dialogs with a fixed path (one path serves pick and save), so a DevTools-driven session can run the flows without OS input. Release builds do not read the variable.
**Rationale:** A restore that merged would change ids and could not give an identical round trip; replacing from the JSON export would restore references that mean nothing on another device. Plan-then-apply keeps parser tests free of a data folder and makes a failure leave tree and vault as they were. Reusing the vault file format would couple two version numbers and invite a backup password that is secretly another vault's master password; the small `seal_with_password` reuses the audited key derivation and AEAD code instead.
**Rejected alternatives:** Merging a full backup; replacing from the connections JSON; reusing the vault file format for backups; sending the decrypted plan to the UI and back; a path chosen by the webview; one vault save per imported entry (replaced on 2026-11-17 by `add_entries_with_ids`, see "M5 final review fixes").

## 2026-11-16 – M5 mRemoteNG format facts and mapping
**Context:** The importer (`crates/fernjo-import/src/mremoteng/`) targets the owner's stable mRemoteNG 1.76. The format facts were read from the mRemoteNG v1.76.20 source (`AeadCryptographyProvider`, `Pkcs5S2KeyGenerator`, `XmlConnectionsDecryptor`); mRemoteNG is GPL, so its source was read to learn the format and **never copied**.
**Decision:** **Supported:** `ConfVersion` 2.6 only (`EncryptionEngine` `AES`, `BlockCipherMode` `GCM`); anything else is `unsupported_format` with a message naming what was found. **Out:** 2.7 and 2.8 are pre-release formats with a separate credential repository and no `Password` attribute (the importer says so and stops); legacy files below 2.6 (AES-CBC, possibly whole-file encrypted and not XML) are on the backlog. **Secret layout:** `base64(salt[16] ‖ nonce[16] ‖ ciphertext ‖ tag[16])`, AES-256-GCM with the 16-byte nonce and the 16-byte salt as associated data; key = PBKDF2-HMAC-SHA1 over the UTF-8 password bytes, the salt and `KdfIterations`, 32 bytes. `KdfIterations` (root attribute, default 1000 when absent) must be within 1000..=1 000 000 (mRemoteNG enforces the lower bound; the upper is ours so a hostile file cannot spin the importer), otherwise `damaged`. **Which key:** the default key is `mR3m`; the root attribute `Protected` decrypts to `ThisIsNotProtected` with the right key. Without a typed key `mR3m` is tried and a failure is `key_needed`; a typed key that fails is `wrong_key`. A decryption error on a single node's `Password` is not fatal: the node imports without a password and the report names it. **Full-file encryption:** with `FullFileEncryption="true"` the root's text is one secret whose plaintext is the inner `Node` elements; it is decrypted, wrapped in a `Connections` element and parsed as usual. **Limits:** 32 MiB file (also the read cap of the command layer, which checks the size from the metadata first; a connections export or backup is read up to 64 MiB, `MAX_OTHER_BYTES`, error `too_large`, so an encrypted backup above 64 MiB never reaches `open`, and the connections importer's own limit of 32 MiB gives `invalid` for a file between 32 and 64 MiB), UTF-8 with optional BOM (UTF-16 is refused with a hint), 59 container levels (the core's tree depth limit of 60 minus the new import folder, see "M5 final review fixes"), 100 000 nodes (`too_large`, `too_complex`), and a work budget of 20 000 000 PBKDF2 iterations in all (`too_complex`, see the same entry). **roxmltree 0.21.2:** DTDs are refused (`allow_dtd: false`, so there are no entity expansions) and a DOM node limit of 2 000 000 is set. Known theoretical weak point, accepted: the parser's duplicate-attribute check is quadratic in the number of attributes of one element, so a single element with millions of attributes within the 32 MiB cap could be slow; the owner picks the file, so this is not treated as an attack surface. **Mapping (as implemented):** the root is not imported, its children go into one new top-level folder `Imported from mRemoteNG (YYYY-MM-DD)`; `Type="Container"` is a folder (kept even if every child is skipped); `Connection` (also a missing `Type`) with `Protocol` `SSH2` or `RDP` (case-insensitive) is an SSH or RDP connection; `Name` (empty becomes "Unnamed" and a problem line), `Descr`, `Hostname` (empty is a problem line) and document order are kept, `Id`, `Expanded`, icons and panels are not. Inheritance is mapped faithfully per setting, folders included: `Port` is unset when `InheritPort` is true or the value is missing, and a port that is 0, above 65535 or not a number is a problem line and unset (`port_invalid` is the reader's field for the not-a-number case); `Username` is unset when `InheritUsername` is true or the value is empty. A password becomes a vault entry only when `InheritPassword` is false and the decrypted password is not empty; the entry carries the node's username and domain when their inherit flag is false and the value is not empty, and the node references it as `settings.credential`. **Deduplication:** entries with the same (username, domain, password) are one shared entry (the lookup uses a per-process keyed hash only to narrow candidates; a hit is confirmed by comparing the real passwords). **Empty-own-password rule:** `InheritPassword="false"` with an empty password means "no password" in mRemoteNG, but an unset fernjo setting inherits; the connection is therefore listed under partly mapped when a folder above sets a credential ("now uses the credential of folder X"), and likewise for an own empty username; no empty-secret entries are invented. A domain without a password to attach it to is partly mapped (fernjo has no domain setting before M7). Entry names are `username` or `username@domain`, with " (2)" and so on when taken; an entry without a username is named after the first node that uses it. **Report:** counts (folders, SSH, RDP, credentials, shared credentials, skipped, partial, problems) and three lists, each capped at 200 lines plus an "and N more" line, each line cut to 200 characters; names, paths and protocols only, never a password. **Skipped** (listed with path and protocol or type): protocols other than SSH2 and RDP (`SSH1`, `VNC`, `Telnet`, `Rlogin`, `RAW`, `HTTP(S)`, `ICA`, `IntApp`, or none) and nodes with an `Unknown` `Type` including everything below them. **Partly mapped:** a non-empty `PuttySession` other than `Default Settings`, one aggregate line that RDP display, redirection and gateway settings are not carried (when there are RDP connections), the empty-own-value cases and the domain case above. **Problems:** a port that is invalid or out of range, a missing name or host, a password that could not be decrypted (the line says "imported without one", or, when a folder above sets a credential and the node therefore inherits it, that it now uses that credential). **Import without passwords** has its own report, worked out with the plan before the line caps: no credentials, no "now uses the credential of folder X" lines, one line (first in the list, so the cap never cuts it) saying how many stored password references were left out. **Wording:** the mRemoteNG file errors say "key" (`key_needed`, `wrong_key`: the field is labelled "Custom key"); the backup errors keep "password". **Independent vectors:** the known-answer ciphertexts and the whole-file fixtures (`crates/fernjo-import/tests/fixtures/`) are produced by `tools/mremoteng-vectors.cs`, a file-based .NET script using BouncyCastle.Cryptography (not the RustCrypto code under test), and are committed, so CI never needs dotnet. **Open (not verified):** the fixtures' attribute set is written from the documented format; the optional validation against mRemoteNG's `mremoteng_confcons_v2_6.xsd` was **not** done (the script has no `--xsd` option) and no real exported `confCons.xml` from the owner has been read by the importer. Verify when the XSD or a real file is available: validate the committed fixtures against the XSD (for example `xmllint --noout --schema mremoteng_confcons_v2_6.xsd crates/fernjo-import/tests/fixtures/default-key.xml`; the full-file fixture has no node elements to validate against the XSD) and import the real file through the Import & backup dialog.
**Rationale:** The owner runs the stable 1.76 line, which writes 2.6; supporting only what was verified against the source keeps the importer small and its errors honest. A faithful per-setting mapping gives every child exactly what it got in mRemoteNG; the report lists everything that could not be carried, so nothing is dropped silently.
**Rejected alternatives:** Supporting 2.7/2.8 (pre-release, different credential model, nothing to test against); legacy CBC (backlog); simplifying inheritance (a child would silently change its username or port); inventing empty-secret entries to express "no password"; copying mRemoteNG source or its fixtures (GPL); a hand-written XML scanner.

## 2026-11-17 – M5 final review fixes
**Context:** The review of the whole M5 branch found seven real problems (dead tabs after a restore, a depth limit looser than what `connections.json` loads, a decrypted plan outliving the dialog, a hostile `confCons.xml` hanging the importer, an import that blocked the main thread and saved the vault once per entry, a newer backup reported as damaged, an unproven round-trip criterion) and a handful of smaller ones. This entry records the decisions behind the fixes.
**Decision:** **Tree depth:** `fernjo_core::MAX_TREE_DEPTH` = 60 levels (top level is 1). `serde_json` reads `connections.json` with a recursion limit of 128 nested JSON levels; each node costs two (object, `children` array) and a connection's `settings` one more, so a connection at level 62 still loads, both from the file and from a backup body (`the_depth_limit_leaves_a_margin_below_what_the_loader_accepts` in `store.rs` finds the edge by parsing, so a change of the format is noticed). 60 keeps a margin of two levels. `Tree::graft` and `Store::replace_tree` refuse more with `TreeError::TooDeep` (code `too_deep`) and write nothing; `backup::open` calls a body tree deeper than that `damaged` (deeper than the JSON parser accepts is `damaged` anyway); the mRemoteNG reader limits containers to 59 levels (`too_complex`) and the connections importer the file's nodes to 59 (`invalid`), so that the new top-level import folder fits. **Not covered, follow-up:** creating or moving nodes by hand (M2) is not checked against the limit, so a tree built by hand beyond 60 levels still saves, may fail to load past about level 62, and its backup would be refused at restore as damaged; the fix belongs to a change of the M2 rules and is not part of M5. `Tree::graft` collects the existing ids in one `HashSet` (O(tree + subtree) instead of a tree search per grafted node). **Work budget:** every `Password` attribute of a confCons file has its own salt and costs one PBKDF2 derivation of `KdfIterations` iterations, so a file of 100 000 nodes at 1 000 000 iterations would occupy a worker for hours (`import_cancel` cannot stop a running derivation). Before any password is decrypted the reader counts the `Password` attributes (a cheap pass that over-counts) and refuses a file whose total, `(key check + full-file body + passwords) x KdfIterations`, exceeds 20 000 000 iterations (`MAX_PBKDF2_ITERATIONS`) as `too_complex` with a message naming the numbers; a full-file body is counted again after it is decrypted. Hundreds of passwords at 1000 iterations (the normal case) use about 2 % of it. **Dev profile:** a debug build of the PBKDF2 loop took minutes for a million iterations; the generic hash code is compiled into the crate that uses it, so `[profile.dev.package.fernjo-import]` and `sha1` are set to `opt-level = 3` in the root `Cargo.toml` (a million iterations then take about 0.3 s; only these two were needed, the other RustCrypto crates the review named add nothing measurable). **Many entries, one save:** `Vault::add_entries_with_ids` adds a batch with one save and `Vault::remove_entries` removes one with one save (rollback); the import path uses both, and `import_apply` is a plain `#[tauri::command]` on an `async fn` that moves the work into `spawn_blocking` (state from the `AppHandle`, like `export_backup`), so a big import does not freeze the window. **Newer backup:** `backup::open` maps `DocumentError::NewerSchema` of the `connections` document to `NewerVersion { found }` (the found number, capped at `u16::MAX`) instead of `damaged`. **Pending plan:** the dialog's `close()` always calls `import_cancel` (harmless when nothing is pending), and `ImportStore` calls it again when a pick, inspect or failed apply finishes after a cancel and nothing newer is going on (a late result must not cancel a newer import). **Restore and tabs:** Rust closes every session without an event, so the UI's snapshot callback gets a `restored` flag and the app calls `sessions.closeAll()` for a restore. **Export:** the password is wrapped in a `SecretString` before the dialog; the password rule, the vault state and the store are checked before the save dialog opens (`export_backup_precheck`); a target inside the data folder (symbolic links and `..` resolved, a not yet existing sub folder included) is refused as `export_target_not_allowed`, so an export can never replace `vault.fernjo` or `connections.json`. **Secret guards:** the no-secret tests now also search for the two other imported fixture passwords (the one with XML and shell metacharacters and the Unicode one, each whole and as the part no JSON or `Debug` escaping changes) and use the sentinel wrong key of the table entry.
**Rationale:** Each rule sits where the thing it protects is decided: depth in the core, so no importer, restore or future caller can write a tree that cannot be read again; the budget in the reader, before the expensive step; one vault save per batch because a vault save is a full serialise, encrypt, write and copy.
**Rejected alternatives:** Making hand-made trees obey the depth limit in this wave (changes M2 behaviour); a time limit or a cancel flag for the PBKDF2 loop (the count is known in advance, so refusing is simpler and cheaper); a lower `KdfIterations` cap (legitimate files use up to a few hundred thousand); `opt-level = 3` for the whole workspace in dev builds.

## 2026-11-16 – M5 dependencies
**Context:** The new crate `fernjo-import` and the import commands need XML parsing, the mRemoteNG crypto primitives and a date source. `cargo deny check` must stay green.
**Decision:** Workspace dependencies in `Cargo.toml` (versions as in `Cargo.lock`): `roxmltree` 0.21.2 (read-only DOM, no external entities), `aes-gcm` 0.11.1 (feature `zeroize`; AES-256-GCM with a 16-byte nonce through `AesGcm<Aes256, U16>`), `pbkdf2` 0.13.0 (feature `hmac`), `sha1` 0.11.0 (PBKDF2's PRF), `base64` 0.23.1 (an older 0.21.7 is also in the lock through other dependencies). `unicode-normalization` 0.1.26 was already a workspace dependency (NFC of the backup password and its length check). `chrono` 0.4.45 was already in the lock (through russh-util) and is declared in `src-tauri/Cargo.toml` with default features off and the `clock` feature, for the local date of the folder names (`today_local`) and the UTC timestamps. The .NET script `tools/mremoteng-vectors.cs` uses `BouncyCastle.Cryptography` 2.6.2 (script only; not part of the build or CI).
**Rationale:** RustCrypto crates match the vault's choice and need no new vetting category. `chrono` was already compiled into the tree.
**Rejected alternatives:** `time` for the local date (`OffsetDateTime::now_local` fails on Unix once the process is multithreaded); a hand-written XML scanner; BouncyCastle-style bindings in Rust (the .NET script is the independent implementation precisely because it is not our code).

## 2026-11-16 – M4 SSH behaviour: known_hosts, timeouts, keepalive, agent limit
**Context:** Details of the SSH layer (`crates/fernjo-ssh`) that are not obvious from the code and that the owner would otherwise ask about again.
**Decision:** **`known_hosts`:** fernjo has its own file `<data folder>/known_hosts` (OpenSSH format, so `ssh-keygen -F` and `-R` work on it; never `~/.ssh/known_hosts`, which fernjo neither reads nor writes). Matching is a byte-based matcher in `known_hosts.rs`, not `russh::keys::known_hosts::known_host_keys_path` (russh 0.65.1): that helper fails the whole lookup on one unparsable key line, does not count comment lines in the line numbers it reports and mishandles CRLF and a leading BOM, and the file is shared with OpenSSH where all of that occurs. Supported patterns are exact names (`host`, `[host]:port`) and hashed `|1|` entries; the host name is lowercased before matching and writing. A rewrite only touches the lines fernjo owns, every other byte stays, and a `.bak` is kept. **Limitation:** `@revoked` and `@cert-authority` lines (and wildcard or negated patterns) are never honoured and never touched: a revoked key in a hand-edited file is not rejected by fernjo. **Connect timeout:** `ConnectParams.connect_timeout` (default 15 s) bounds each wait for the server separately (TCP connect and handshake, each authentication round trip, the PTY request), and the clock is paused while a user prompt is open; it is deliberately not one total budget, because a person typing a password or comparing a fingerprint must not burn the budget of the network. **Agent sign step:** it shares that timeout, so an agent that needs a touch or a confirmation for each signature (hardware key, `ssh-add -c`) times out after 15 s of waiting; recorded as a known limitation and in the backlog. **Keepalive:** `keepalive_interval` is the connection's value (default 30 s, 0 turns it off) with russh's `keepalive_max: 3`; russh ends the connection on the 4th unanswered tick (it counts after sending), so a dead peer is noticed after about 4 intervals (about 120 s by default), not 3.
**Rationale:** An own, tolerant matcher keeps a user-edited file usable and keeps unknown lines intact; per-stage timeouts match what the user perceives as "the server is not answering".
**Rejected alternatives:** The russh helper (see above); reading `~/.ssh/known_hosts` (fernjo's data folder is meant to be self-contained and syncable, and a rewrite of the shared file is risky); one total connect budget (breaks with slow typists); honouring `@revoked` now (needs a policy for what fernjo does with a revoked key it must not delete).

## 2026-11-16 – M4 flow control numbers
**Context:** `yes` or `cat` of a big file must not freeze the UI or make Ctrl+C wait behind megabytes of queued output. Complements the flow-control paragraph of "M4 session IPC". Requirement: after `yes` has run for 5 s, Ctrl+C returns the prompt within 1 s.
**The mechanism (corrected):** the echo of Ctrl+C is ordered behind every byte of output the server has already sent, so all of it must drain through xterm.js's parser before the prompt can appear; the latency is (data in flight between the server and the parser) divided by the parser's speed, plus the round trip. The data in flight is the sum of every buffer in the pipe: the SSH window (the server may send this much before russh sends a window adjust; russh adjusts when it *receives* a packet, not when the consumer has read it), russh's per-channel packet buffer (`channel_buffer_size`, 32 KiB packets), the event queue of `fernjo_ssh` (`EVENT_QUEUE`), the unacknowledged bytes in the webview (`HIGH_WATER`) and one more batch (`MAX_BATCH`). The first version did not look at the first two and documented only the last three.
**Before (russh defaults plus the first numbers):** window 2 MiB + channel buffer 100 x 32 KiB = 3.1 MiB + `EVENT_QUEUE` 64 x 32 KiB = 2 MiB + `HIGH_WATER` 256 KiB + one 64 KiB batch, about 7.4 MiB in flight (`LOW_WATER` 64 KiB, `MAX_BATCH` 64 KiB).
**Decision (after):** `client_config` in `crates/fernjo-ssh/src/session.rs` sets `window_size` 512 KiB and `channel_buffer_size` 4 (packet size stays 32 KiB); `EVENT_QUEUE` 4 (also in `session.rs`); `session_flow.rs`: `HIGH_WATER` 128 KiB, `LOW_WATER` 32 KiB (the forwarder pauses above the first and resumes at or below the second); `sessions.rs`: `MAX_BATCH` 32 KiB (one SSH packet), batches every 16 ms. Data in flight: 512 + 4 x 32 + 4 x 32 + 128 + 32 KiB, about 0.9 MiB, a tenth of before.
**Measured** (Windows 11, release binary, ten tabs, `htop` in one, `yes` in another for 5 s, Ctrl+C in the `yes` tab, WebGL renderer, time from the key event to the first compositor frame that shows the new screen, six rounds per run, fresh test container per run): single tab, earlier tasks: 80 to 165 ms. Ten tabs, before: 259 to 1386 ms over eight runs of six rounds on the old build (8 of 48 rounds above 1 s; the first measurement gave 296 to 1670 ms). Ten tabs, after, two runs of six rounds: 487, 476, 471, 457, 489, 379 ms and 412, 368, 545, 281, 479, 331 ms (all twelve under 1 s, the worst 545 ms). Smaller pipes tried with the same method (one run each) gave 148 to 257 ms (window 128 KiB, one buffered packet, one queued event, `HIGH_WATER` 128 KiB) and 198 to 260 ms (the same with `HIGH_WATER` 32 KiB), so the in-flight bound is what the latency follows; the chosen numbers keep more headroom for throughput. (Measurement note: an early series of these runs accidentally drove the old binary, because the copies of the app were named differently from the process the script stopped and the single-instance plugin let the old one keep running; the numbers above for "after" and the smaller pipes are from runs where the new binary's process was confirmed.)
**Trade-off (throughput):** in-app throughput is limited by `HIGH_WATER` divided by the round trip of the acknowledgement (xterm parse, `session_ack` invoke, wake-up of the forwarder) and, at the top, by xterm.js itself. `yes` with 92-byte lines (50 MB, release binary, WebGL): 2.4 MB/s before (`HIGH_WATER` 256 KiB), 1.3 to 1.4 MB/s after (128 KiB), 0.8 MB/s with 32 KiB. A raw 30 MB transfer through `fernjo-ssh` alone (test `bulk_output_throughput_stays_high_with_the_small_window`) runs at 3 to 6 MB/s on this machine with the old and the new window alike, so the Docker loopback and the cipher are the limit there and the window is not; the figure of 15 MB/s that was proposed as a floor is not reachable on this setup with either configuration. The SSH window also bounds throughput on a slow link (window divided by the round trip: 512 KiB at 50 ms is about 10 MB/s, at 200 ms about 2.5 MB/s), enough for a terminal. If big `cat`s on fast links matter more than Ctrl+C under `yes`, raise `HIGH_WATER` first (the in-app limit) and re-measure.
**Rationale:** The requirement is about interactivity, which the bound on data in flight decides; bulk throughput of a terminal is bounded by xterm.js anyway.
**Rejected alternatives:** Dropping output when behind (corrupts escape sequences); no flow control (memory grows with the slowest renderer); discarding queued output when Ctrl+C is typed (the UI cannot know what the program will still print).

## 2026-11-16 – M4 clipboard path
**Context:** The terminal needs copy and paste in a Tauri webview on three engines. `navigator.clipboard.readText()` in WebView2 shows a permission prompt and the promise stays pending until the user answers, so a naive paste hangs.
**Decision:** Copy uses `navigator.clipboard.writeText` from the user gesture (works without a prompt). Keyboard paste (Ctrl+Shift+V, Cmd+V) is not intercepted: the native `paste` event delivers the text and is passed to xterm.js, so no permission is involved. The context-menu "Paste" has no paste event and uses `readText()` with a 2.5 s timeout; on timeout it gives up silently and the keyboard shortcut remains the dependable path. **Not done:** Rust clipboard commands. The usual crate `arboard` pulls `clipboard-win` on Windows, which is BSL-1.0, and `deny.toml` does not allow BSL-1.0; allowing a new licence is a policy decision for the owner (backlog: "Native clipboard commands").
**Rationale:** The browser path covers the daily cases without new dependencies, permissions or licences.
**Rejected alternatives:** `tauri-plugin-clipboard-manager` (needs a capability for the webview and the same crate family); calling `readText()` without a timeout (hangs the menu item on WebView2).

## 2026-11-16 – M4 terminal: xterm.js versions, WebGL policy, no lazy import
**Context:** M4 adds the terminal to the UI.
**Decision:** `@xterm/xterm` 6.0.0 with the addons `@xterm/addon-fit` 0.11.0, `@xterm/addon-webgl` 0.19.0, `@xterm/addon-search` 0.16.0 and `@xterm/addon-web-links` 0.12.0, pinned exactly in `package.json`. **WebGL** is attached only to the terminal of the visible tab and disposed when the tab goes to the background (browsers cap the number of WebGL contexts at about 16 per page, and ten or more tabs are expected); it also falls back to the DOM renderer when a context is lost or cannot be created (WebKitGTK). **No lazy import:** the terminal is part of the main chunk, which grew from 123 kB to 632 kB (173 kB gzip). This is a local app that loads the bundle from disk, so the cost is parse time, not download; a lazy chunk would add a loading state to the first tab for no measurable gain. `build.chunkSizeWarningLimit` in `ui/vite.config.ts` is raised so the build does not warn about this known size.
**Rationale:** One WebGL context at a time stays far below every limit and costs nothing for hidden tabs.
**Rejected alternatives:** WebGL in every tab (context limit); `import()` of the terminal (see above); the canvas addon (removed in xterm.js 6).

## 2026-11-16 – M4 session IPC: raw output channel, raw input body, flow control, opener plugin
**Context:** Terminal sessions stream bytes both ways and ask the user questions while connecting. The Tauri 2 API (`tauri` 2.12.5 as in `Cargo.lock`, source read in the cargo registry before use) decides what the wire can look like.
**Decision:** **Output:** one `tauri::ipc::Channel<InvokeResponseBody>` per session carries both kinds of messages: terminal output as `InvokeResponseBody::Raw` (the JS handler receives an `ArrayBuffer`, via `new Uint8Array(...).buffer` below 1 KiB or the fetch path above it) and events as `InvokeResponseBody::Json` (the handler receives the parsed object). The UI tells them apart with `instanceof ArrayBuffer`; the JS `Channel` re-orders by the message index Tauri adds, so output and events stay in order. A typed `Channel<SomeEnum>` would force output through JSON (a number array), which is why the untyped body is used. The wire contract is documented at the top of `src-tauri/src/sessions.rs`; the Rust event type is `UiEvent` (the name `SessionEvent` is taken by `fernjo_ssh`). **Input:** `session_input` takes `tauri::ipc::Request` and reads `InvokeBody::Raw` (the webview invokes with a `Uint8Array`), the session id in the header `x-fernjo-session`; a JSON body or a missing header is `invalid_request`. Input, resizes and close go through one ordered queue per session (an unbounded `mpsc`, drained by a writer task) because separate async commands may overtake each other. **Flow control:** output is batched (16 ms or 32 KiB, in messages of at most 32 KiB); the forwarder counts sent bytes, the UI reports written bytes with `session_ack`; above 128 KiB unacknowledged it stops reading from the SSH layer until the count falls to 32 KiB (hysteresis). The SSH layer's event queue (4 events) and russh's channel buffer (4 packets) are bounded, and the SSH window is 512 KiB, so the server is held back and memory stays bounded; the full budget, the measurements and the trade-offs are in "M4 flow control numbers" (the numbers first written here, 256 KiB / 64 KiB / 64 KiB and the 2 MiB window and 100-packet buffer of russh's defaults, were too large to meet the Ctrl+C requirement with ten tabs). **Closing:** `close_session` is silent (the channel is muted first), answers every open prompt with the safe answer (reject, no secret), aborts the connect task and drops the entry. **Plan resolution** happens synchronously inside `open_session`, `resume_session` and `reconnect_session` (the spawned task needs no `AppState`); reconnect resolves again from the tree as it is, a deleted node ends as `disconnected` with "the connection no longer exists". **Opener plugin:** `tauri-plugin-opener` 2 (2.7.3 as resolved in `Cargo.lock`), registered after the dialog plugin and used only through its Rust API (`OpenerExt::opener().open_url`) in the command `open_external_url`, which accepts only absolute `http`/`https` URLs with a host (else `invalid_url`). `capabilities/default.json` stays `["core:default"]` (guarded by `src-tauri/tests/tauri_conf.rs`), so the webview cannot call the plugin's own commands or open arbitrary paths and schemes.
**Rationale:** Raw binary in both directions avoids JSON-encoding every byte; one channel keeps events and output ordered; routing the link opening through a validated Rust command keeps the webview's permissions at the minimum, like the dialog plugin.
**Rejected alternatives:** Two channels (events and output; ordering between them is lost); a typed JSON channel for output (large and slow); `Vec<u8>` as a JSON array for input (same cost, and one invoke per keystroke batch); `@tauri-apps/plugin-opener` from the webview (needs a capability and accepts any URL the UI sends); an `AppHandle`/`AppState` clone inside the connect task to resolve plans there (the plan is only needed at start, and resolving in the command reports errors straight to the caller).

## 2026-11-16 – M4 dependencies: russh, ring, RSA advisory
**Context:** M4 adds SSH sessions in the new Tauri-free crate `fernjo-ssh`. The SSH client library and its crypto backend had to be chosen, and `cargo deny check` reports `RUSTSEC-2023-0071` (Marvin Attack, RSA timing side channel) for the `rsa` crate russh uses.
**Decision:** `russh` 0.65.1 (as resolved in `Cargo.lock`) with `default-features = false` and features `flate2`, `ring`, `rsa`; `tokio` 1 with features `rt`, `net`, `time`, `sync`, `macros`, `io-util`. `russh` pins `rsa` 0.10.0-rc.18, which carries the advisory (fixed in `rsa` 0.10.0). The advisory is ignored in `deny.toml` with a reason, time-boxed by an owner decision of 2026-11-16: the ignore is removed as soon as russh depends on `rsa` >= 0.10.0 (re-check with `cargo deny check` after every russh update). `rsa` stays enabled because RSA host keys and RSA user keys are still common on real servers. **Crypto backend:** `ring`, because it builds on Windows without a C toolchain. "Pure Rust" no longer holds for the crypto backend: `ring` contains C and assembly.
**Rationale:** Dropping RSA would make fernjo unusable against many servers; the exposure is a timing side channel on RSA private-key operations (client-side signing with an RSA user key), which is accepted for now and bounded in time by the removal condition.
**Rejected alternatives:** `aws-lc-rs` as backend (needs a C toolchain / CMake on Windows); disabling the `rsa` feature (breaks RSA keys); a permanent, unconditioned ignore.

## 2026-11-15 – Vault: lost-update guard, password change and private key updates
**Context:** An unlocked vault keeps its entries in memory and writes the whole file on every change. A `vault.fernjo` delivered by a sync tool after the unlock (another device added an entry, changed the password, or a newer format arrived) would be silently overwritten, which also broke "a newer format version is refused and never overwritten".
**Decision:** `Vault::save` re-reads the file first and only writes when the file is missing (recreate) or starts with exactly the header bytes this handle last read or wrote (the body nonce changes on every save, so the header identifies the version). Anything else (another header, garbage, empty, shorter than a header, newer format) fails with the new error code `changed_on_disk` ("The vault file was changed by another device or a sync tool. Lock and unlock the vault to load the changes, then repeat your change."); entries and header in memory stay as they were. **Limit:** this is check-then-write, not a lock; a sync tool can still win the race between the check and the rename. **Password change:** the data key never rotates (keychain items must survive), so changing the master password does not re-encrypt or delete existing copies; `vault.fernjo.bak` from just before the change, backups and sync history still open with the old password and yield the data key that decrypts every later version too. This is documented in `Docs/vault-format.md` and in the change-password form; the `.bak` is not refreshed after a change. Real re-keying is not part of M3. **Private key updates:** `update_credential` with a new `privateKey` and no `passphrase` keeps the stored passphrase; `passphrase` sets or replaces it, `clearPassphrase: true` removes it (alone it keeps the key; together with a typed `passphrase` it is refused). The UI offers "Remove stored passphrase" only when editing a private key. **Threads:** the commands that run an Argon2 derivation (`vault_create`, `vault_unlock`, `vault_change_password`) are `#[tauri::command(async)]` so they run off the main thread.
**Rationale:** The guard is cheap, needs no file locking (which sync folders do not honour anyway) and turns a silent data loss into an explicit, recoverable error. Not rotating the key keeps the wrapped-key design of "Vault: wrapped data key, Argon2id, XChaCha20-Poly1305".
**Rejected alternatives:** File locks (not honoured across devices); merging two versions of the vault (needs the key and conflict rules, out of scope); refreshing `.bak` after a password change (it only hides the old copy, the sync history and backups remain); making the new key replace the passphrase silently (data loss the UI field "unchanged" did not announce).

## 2026-11-15 – Vault: secrets and known limitations of zeroisation
**Context:** Secrets must not outlive their use in memory, but the stack between the webview and the keychain contains code fernjo does not own.
**Decision:** Best-effort zeroisation only. Master passwords and entry secrets are `SecretString`/`Zeroizing` inside `fernjo-vault` and the command wrappers; the data key and derived keys are wiped after use. **Known limitations:** secrets pass through unzeroised intermediate `String`s in serde deserialisation (the internally tagged `Secret` enum buffers its content), serde_json buffer reallocations when the vault body is encoded, the Tauri IPC JSON buffer in both directions (the webview process holds the typed secret and, on reveal, the revealed one for as long as the browser engine keeps it), and the `keyring` crate and the OS keychain service. The explicit "reveal" action is the only way a secret reaches the webview, and the UI hides it again after 10 seconds or when the vault locks.
**Rationale:** A guarantee that cannot hold across serde, an IPC layer and a browser engine would be false; the goal is to keep secrets out of files, logs, snapshots and `Debug` output (enforced by tests) and to shorten their lifetime where fernjo controls the memory.
**Rejected alternatives:** A custom deserialiser that parses secrets into zeroising buffers (large code surface for a partial gain); claiming memory-safety guarantees in the docs.

## 2026-11-15 – Data folder change: restart guard
**Context:** The data folder can be changed in the app (M3). Open files, the vault mutex and the keychain id all refer to the running folder, so switching live would risk writing to two folders.
**Decision:** `apply_data_folder` validates the target (absolute, usable, not equal to or nested inside the running folder), copies `connections.json` and `vault.fernjo` only if the target has neither, writes `settings.json` last and then sets `restart_required`; the running app keeps using its old folder until `restart_app`. While the restart is pending, tree and vault commands that write refuse with `restart_required` (`ensure_writable`), so nothing is saved to the old folder after the choice; lock and unlock are allowed (they write no file). Choosing again while pending is allowed (last wins); choosing the running folder cancels the change. If the target already holds data files they are kept untouched and reported in `DataFolderInfo.existingFiles` (names, in the order `connections.json`, `vault.fernjo`); the dialog warns that this folder's data will be used instead of the current data. A failing copy rolls back the files already placed (`copy_failed`). The choice is refused with `data_dir_locked_by_env` when `FERNJO_DATA_DIR` is set, with `settings_unusable` when `settings.json` is unreadable or from a newer schema (the file is never saved over) and with `no_config_dir` when the OS has no config directory. The old folder stays intact as a backup.
**Update 2026-11-15 (M3 review):** `apply_data_folder` is a plain Rust function, not an IPC command. Only `choose_data_folder` (native picker in Rust) calls it, so the webview can never point the data folder at an arbitrary path.
**Rationale:** Copy-then-restart keeps every failure recoverable and never merges two data sets.
**Rejected alternatives:** Switching live (two data sets in flight); merging a target's existing data with the current data; moving instead of copying.

## 2026-11-15 – Master password: NFC normalisation
**Context:** The same typed password must unlock the vault on Windows, macOS and Linux, where input methods and file systems produce composed or decomposed Unicode.
**Decision:** The master password is normalised to NFC and otherwise used byte-exact (no trimming, no case folding); the minimum length of 8 counts characters after normalisation. Entry secrets (passwords, keys, passphrases) are not normalised; they are stored byte-exact. Details in `Docs/vault-format.md`.
**Rationale:** macOS keyboards and sync tools may deliver decomposed forms; NFC makes the derived key independent of that. Trimming would silently change what the user typed.
**Rejected alternatives:** NFKC (folds characters users consider distinct); no normalisation (a vault created on one OS might not open on another).

## 2026-11-15 – Vault file format
**Context:** The vault file is synced between devices by the user and must stay readable by other tools and later versions.
**Decision:** The file format (version 1: header with vault id, Argon2id parameters, salt, wrapped data key; body encrypted with the data key, whole header as AAD) is specified in `Docs/vault-format.md`, which is enough to write a reader. Parameters (128 MiB, 6 iterations, 4 lanes), load bounds, the NFC rule and the dependency versions are recorded in "M3 dependencies and vault parameters". A newer format version is reported as an unusable vault and never overwritten; saves are atomic (temp file + rename) and keep `vault.fernjo.bak`.
**Rationale:** One normative document next to the code avoids drift; decisions about why live here.
**Update 2026-11-15 (M3 review):** a save refuses to overwrite a file changed on disk since it was read (`changed_on_disk`), and changing the master password does not re-encrypt or delete older copies of the file; both are described in "Vault: lost-update guard, password change and private key updates" and in `Docs/vault-format.md`.
**Rejected alternatives:** A self-describing container such as age or JWE (larger dependency, no wrapped-data-key semantics for the keychain).

## 2026-11-15 – `settings.json` and data folder precedence
**Context:** M3 lets the owner move the data folder, so the app needs a place that says where the data folder is. That place cannot be the data folder.
**Decision:** `settings.json` (`{ "schemaVersion": 1, "dataDir"?: string }`) lives in `<OS config dir>/fernjo/` (`Location::config_dir`); `connections.json` and the vault live in `Location::data_dir`. Precedence: `FERNJO_DATA_DIR` (non-empty) > absolute `dataDir` in `settings.json` > `<OS config dir>/fernjo`. While the variable is set, `settings.json` is neither read nor written, so manual runs never touch the real config. A relative or empty `dataDir` counts as unset. If the variable is set but the OS has no config directory, `config_dir` equals `data_dir` (the override stays usable; nothing is read from it). An unreadable `settings.json` (no usable `.bak`) or one with a newer schema does not stop the app: `locate` falls back to the default folder and puts the `LoadError` in `Location::settings_error` for the app to show; the file is left untouched and callers must not save over it. A corrupt file that is recovered from `.bak` is moved to `settings.json.corrupt-<secs>` so the next save cannot copy it over the good backup. Sync-conflict copies (`sync-conflict`, `conflicted copy`, `_conflict-`) in the data folder are reported as `Notice::SyncConflicts`. The atomic write (`write_atomic`) is shared by `connections.json` and `settings.json`.
**Rejected alternatives:** Keeping `settings.json` in the data folder (circular); failing startup on a bad `settings.json` (the app would be unusable for a recoverable file).

## 2026-11-15 – M3 dependencies and vault parameters
**Context:** Milestone 3 adds `crates/fernjo-vault` (no Tauri, no `fernjo-core`). It needs a password KDF, an AEAD, a secret type, memory wiping, Unicode normalisation and a CSPRNG, all from audited crates, never home-made.
**Decision:** Dependencies (versions as resolved on 2026-11-15, see `Cargo.lock`): `argon2` 0.6.0 (Argon2id), `chacha20poly1305` 0.11.0 (XChaCha20-Poly1305, `XChaCha20Poly1305` with 24-byte nonces), `secrecy` 0.10.3 (`SecretString` for passwords), `zeroize` 1.9.1 (wiping the data key, derived keys and decrypted bodies; the `zeroize` feature is enabled on `argon2` and `chacha20poly1305`, otherwise they do not wipe the Argon2 initial hash and memory blocks or their cipher key copies), `unicode-normalization` 0.1.26 (NFC for master passwords), `getrandom` 0.4.3 (OS randomness for key, salt and nonces; called directly so no `rand_core` trait versions have to line up with the RustCrypto crates). Reused: `serde`, `serde_json`, `uuid`, `thiserror`, dev `tempfile`. `cargo deny check` stays green without new ignores. **Format:** `Docs/vault-format.md`; a random 256-bit data key is wrapped by the Argon2id-derived key, the body is encrypted with the data key and fresh 24-byte nonces on every save; the key wrap authenticates the header up to the wrapped key, the body authenticates the whole header (so a password change, which verifies the old password, picks a new salt and wrap nonce, re-wraps the unchanged data key and saves once, re-seals the small body under the same data key with a fresh nonce; the data key and the entries stay unchanged). **Master password:** at least 8 characters counted after NFC normalisation, no composition rules; NFC-normalised, otherwise used byte-exact (no trimming), so the same typed password unlocks on every OS and keyboard input method. The length rule is enforced when creating or changing a password, not when unlocking. **KDF parameters:** Argon2id with 128 MiB memory, 6 iterations, 4 lanes. Measured 0.52 s per derivation on a 6-core desktop (release build; `cargo test -p fernjo-vault --release -- --ignored --nocapture`), the "about 0.5 s" target. The values are stored in the header, so they can be raised later. The memory-heavy, few-pass choice follows the Argon2 guidance (memory is what slows GPU attackers); 128 MiB is well within every supported machine. Load bounds, applied before deriving: parallelism 1..16, iterations 1..20, memory `8 * parallelism` KiB..1 GiB. `KdfParams::TEST` (8 KiB, 1 pass, 1 lane) is the smallest accepted value and exists for tests only. The workspace `Cargo.toml` compiles `argon2` and `blake2` with `opt-level = 3` in the dev profile; unoptimised Argon2 is about 30 times slower and would make unlock take several seconds in `pnpm tauri dev` and in tests that use the default parameters.
**Also in M3:** `keyring` 4.2.0 and its OS stores (see "Vault: keychain behaviour") and `tauri-plugin-dialog` 2.8.4 (see "Data folder dialog").
**Rationale:** RustCrypto crates are the standard pure-Rust, permissively licensed implementations, with no system library on any target. XChaCha20-Poly1305 has a nonce large enough to pick at random on every save without a counter, which matters for a file that is synced between devices.
**Rejected alternatives:** `rand` as the randomness source (an extra dependency and trait-version coupling for filling a few byte arrays); AES-GCM (12-byte nonces make random nonces on a long-lived synced file less comfortable); scrypt or PBKDF2 (Argon2id is the current recommendation and resists GPUs better); encrypting the body directly with the password-derived key (a password change would re-encrypt everything and the keychain could not hold a password-independent key).

## 2026-11-15 – IPC content security policy

**Decision:** The CSP gains `connect-src ipc: http://ipc.localhost` (everything else unchanged: `default-src 'self'`, no `unsafe-eval`). `src-tauri/tests/tauri_conf.rs` now requires that exact `connect-src`, rejects the token `*` and `unsafe-eval`, and allows no `http:`/`https:` token other than `http://ipc.localhost`. ## 2026-11-15 – Pointer-based drag and drop in the tree
**Context:** M2 needs moving nodes by drag and drop in a nested tree with three drop zones per folder (before, inside, after). The owner's Linux setup is Wayland with WebKitGTK.
**Decision:** The tree is dragged with pointer events (`pointerdown`/`pointermove`/`pointerup`, pointer capture once a 4 px threshold is crossed). A pure function (`ui/src/lib/drop-target.ts`, `dropPosition` and `resolveDrop`) maps the pointer to a drop (new parent and index, counted after the dragged node is removed, the same convention as the Rust `move_node`); a DOM-free `DragController` holds the state machine. Rust validates every move; the only call is `move_node`. Dragging is off while a filter is active or a rename is open; Escape cancels.
**Rationale:** Native HTML5 drag and drop needs `dragDropEnabled: false` in the Tauri window and is the least reliable on WebKitGTK/Wayland; the pointer approach behaves the same in all three webviews and is unit-testable without a browser.
**Rejected alternatives:** Native HTML5 drag and drop; a Svelte drag-and-drop library (not built for nested trees with three drop zones, extra dependency).

## 2026-11-15 – `connections.json`: format, location, write strategy
**Context:** M2 persists the connection tree; later milestones add settings (credential reference in M3, RDP in M7) and import (M5). The file must survive crashes and newer app versions, and must never hold a secret.
**Decision:** The tree lives in Rust (`fernjo-core`, a pure `Tree` plus a `Store` that saves after every mutation); every mutating Tauri command returns the full new snapshot and the UI renders snapshots (the UI keeps only selection, expansion, filter and drag state). Delete asks for confirmation and is final; `connections.json.bak` is the only safety net. **Format:** `connections.json`, pretty-printed UTF-8 JSON, `{ "schemaVersion": 1, "children": [ … ] }`, nodes nested: `{ "id" (UUID v4), "type": "folder"|"connection", "name", "description", "settings": { "username", "port", "keepaliveSecs" } (omitted keys = inherit), and either "children": [ … ] or "protocol": "ssh"|"rdp", "host" }`. Order is the position in `children`. No credential field exists. Inheritable in M2: username, port, keepalive; effective value = nearest value from the node up through its folders, then the default (SSH 22, RDP 3389, keepalive 30 s with 0 = off, no username; a folder's port has no default). **Location:** `<OS config dir>/fernjo/` (`%APPDATA%\fernjo`, `~/Library/Application Support/fernjo`, `~/.config/fernjo`), overridden by the environment variable `FERNJO_DATA_DIR` (tests, the sample-tree generator). **Write:** temp file in the same folder, `sync_all`, copy the current file to `connections.json.bak`, rename the temp file over the target; a failed save leaves memory unchanged (the mutation is applied to a copy first). **Load:** a missing file is an empty tree (created by the first mutation); a `schemaVersion` newer than the app is refused and never overwritten; an unreadable file falls back to `.bak` after being renamed to `connections.json.corrupt-<unix seconds>` (so a later save cannot replace the good `.bak` with garbage) and the UI shows a notice; if both are unreadable the app starts in an error state and writes nothing. Migration is a chain of version N → N+1 functions (empty for now, tested). **Update 2026-11-15 (M3, schema 2):** `schemaVersion` is now 2 and `settings` gains an optional, inheritable `credential` (vault entry UUID, omitted = inherit; resolved like `port`, no default; the core never knows the vault, so the id may dangle). The 1 → 2 migration step is a no-op that exists only so older builds refuse the file (they would drop `credential` on their next save); a version-1 file loads and is written as version 2 on the next save (the version-1 bytes stay in `.bak`), version 3 is refused as a newer schema. The "No credential field exists" sentence above applies to schema 1 only.
**Rationale:** Rust ownership keeps validity and inheritance in one tested place, and a snapshot per mutation (~170 KB at 500 connections) is simple and cannot drift. The write sequence never leaves a half-written main file; the load rules never destroy data the user might still want.
**Rejected alternatives:** UI-owned tree pushed to Rust (logic would drift into TypeScript); diff or event streams (complexity with no benefit at this size); instant delete with an undo toast (needs an undo history in the core); `directories`' `ProjectDirs` layout (adds a `config` subfolder on Windows); renaming the temp file over the old one without a `.bak` copy.

**Rejected alternatives:** A third-party toolchain action (extra supply-chain surface); `gitleaks-action` (licence); an OS matrix in M0 (cost without a packaging step to test); enabling `unsound = "all"` now (would fail on a Tauri-internal advisory we cannot fix).

## 2026-11-15 – cargo-deny: licence allow-list and advisory ignores
**Context:** M0 adds a `cargo-deny` CI job (advisories, bans, licences, sources) that must be green on the workspace including Tauri's dependency tree (cargo-deny 0.20.2, run with `--all-features`; the graph covers all platforms, so Linux-only crates are checked too).
**Decision:** `deny.toml` allows only `MIT`, `Apache-2.0`, `Apache-2.0 WITH LLVM-exception`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `Zlib`, `Unicode-3.0`, `CC0-1.0`, `MPL-2.0`; no licence was added beyond this starting list (the first run reported no licence violations). Sources are crates.io only (unknown registry and git denied); duplicate versions only warn. One advisory is ignored: `RUSTSEC-2024-0370` (`proc-macro-error` unmaintained, pulled in by `glib-macros` through Tauri's Linux GTK3 stack; no safe upgrade exists). Remove the ignore when Tauri moves off GTK3 (or `glib-macros` drops `proc-macro-error`); `cargo deny check` will then report the entry as unused, as a *warning* (not an error), so look for it in the output after Tauri upgrades. Wildcard dependencies are not allowed (default `warn` is not loosened) and the licence confidence threshold stays at its default.
**Rationale:** The allow-list is limited to permissive licences and MPL-2.0 (weak copyleft), all compatible with distribution under `MIT OR Apache-2.0`. The ignore is a single, id-specific entry with a reason: the crate is a build-time proc macro we cannot replace, and it is an unmaintained notice, not a vulnerability.
**Rejected alternatives:** Disabling the unmaintained check (`unmaintained = "none"`) or blanket-ignoring advisories (would hide future findings); allowing licences speculatively (every addition should be driven by a real finding); skipping crates in the licence check.

## 2026-11-15 – Public repo, CI only on GitHub-hosted runners
**Context:** Tauri on Linux needs WebKitGTK system packages; the org's self-hosted runner (`dotnet-linux`) has no root. Release builds need macOS and Windows machines. Hosted-runner minutes cost money on private repos.

## 2026-11-15 – Vault: wrapped data key, Argon2id, XChaCha20-Poly1305
**Context:** Credentials must be stored encrypted, the vault file may be synced between devices by the user, and "unlock automatically on this device" uses the OS keychain.
**Decision:** A random 256-bit data key encrypts the whole vault file; the master password derives (Argon2id) a key that wraps the data key. The OS keychain stores the data key. RustCrypto crates only.
**Rationale:** Changing the master password only re-wraps the data key, so keychain entries on other synced devices stay valid; no home-made crypto.
**Update 2026-11-15 (M3):** The statement above is imprecise: a password change re-wraps the data key and re-saves the file, and the body is re-sealed with a fresh nonce because the whole header is its AAD (see "M3 dependencies and vault parameters"). The data key and the entries stay unchanged, so keychain entries stay valid.
**Rejected alternatives:** Storing the password-derived key in the keychain (invalidated on every password change); OS keychain as the only store (does not sync across OSes, no portable backup).

## 2026-11-15 – Vault: keychain behaviour
**Context:** "Unlock automatically on this device" needs the data key in the OS keychain, without a system C library on Linux.
**Decision:** `keyring` 4.2.0 (with `keyring-core` 1.0.1) with its default `v1` feature, which selects per OS: `windows-native-keyring-store` 1.1.0 (Credential Manager), `apple-native-keyring-store` (macOS Keychain) and `zbus-secret-service-keyring-store` 1.0.1 (Secret Service over `zbus`, no libdbus; `cargo tree -p fernjo-vault --target x86_64-unknown-linux-gnu` shows no `dbus` crate). Item: service `fernjo`, user = vault id, secret = the 32 raw key bytes (`DataKey`, wiped after use). Auto-unlock (`try_auto_unlock`) never prompts: a missing item gives `NoKey`, a keychain error `Unavailable`, a key that fails authentication (`tampered`) deletes the item (`StaleKeyRemoved`); the vault stays locked in all of these and the UI falls back to the master password. A master password change keeps the data key, so stored keys stay valid. **Trade-off:** any `tampered` result from `unlock_with_key` deletes the keychain item, including the case of a corrupted or half-synced vault body with a valid key; the user then has to unlock with the master password and enable auto-unlock again. **Other readers of the keychain:** a second launch of the app (single-instance) also runs the auto-unlock attempt before it exits, so it reads the keychain, may delete a stale item and, on macOS, may trigger a keychain prompt. `lock` never touches the keychain (the lock lasts until the next start); `set_auto_unlock(true)` surfaces a keychain error (`keychain_unavailable`), while a keychain failure on unlock or create is ignored and only leaves `autoUnlock` false.
**Update 2026-11-15 (M3 review):** because the data key never rotates, changing the master password does not lock out the old password for older copies of the vault file (`vault.fernjo.bak`, backups, sync history): they still open with the old password and the key they yield decrypts every later version. Real re-keying is not in M3. Unticking "Unlock automatically on this device" in the lock note now removes the keychain item after a successful unlock (the UI calls `vault_set_auto_unlock(false)`; `vault_unlock` with `remember: false` itself never deletes the item).
**Threat model:** With auto-unlock on, the data key is readable by anything running as the same OS user, so such a process can open the vault. Auto-unlock is therefore an explicit opt-in per device; the master password protects the vault file when it is copied or synced elsewhere.
**Rejected alternatives:** `dbus-secret-service` / `linux-keyutils` stores (libdbus or kernel keyring without persistence); storing the password-derived key (see above).

## 2026-11-15 – SSH via russh, RDP via IronRDP
**Context:** The core must be Rust; SSH is used more than RDP.
**Decision:** russh (tokio) for SSH; IronRDP for RDP, rendered through a framebuffer streamed to a canvas. The RDP milestone starts with a measured spike; a native render surface is the fallback (its own milestone if needed).

## 2026-11-15 – Data folder dialog: tauri-plugin-dialog (Rust API only)
**Context:** M3 lets the user pick the data folder; the native folder picker must open from Rust and the webview must gain no new permissions.
**Decision:** `tauri-plugin-dialog` 2.8.4 (`tauri-plugin-dialog = "2"`), registered after the single-instance plugin and used only through its Rust API (`DialogExt::file().blocking_pick_folder()` on a `spawn_blocking` worker). No JS permission is added: `capabilities/default.json` stays `["core:default"]` (guarded by `src-tauri/tests/tauri_conf.rs`), so the webview cannot call the plugin's own commands. `apply_data_folder` copies `connections.json` and `vault.fernjo` only into a folder that has neither of them, writes `settings.json` last and then sets `restart_required`; the running app keeps its old folder until `restart_app`.

## 2026-11-17 – M6 packaging: targets, per-user NSIS, one version source, release profile
**Context:** M6 turns the app into installers for Windows, macOS and Linux that a user can install without developer tooling.
**Decision:** `bundle.targets` is exactly `nsis`, `dmg`, `appimage` and `deb` (guarded by `src-tauri/tests/tauri_conf.rs`). The NSIS installer is per-user (`installMode: "currentUser"`, English only), so an unsigned tool needs no administrator rights. `tauri.conf.json` has no `version` key: Tauri falls back to the `fernjo-app` crate version, which inherits `[workspace.package].version`, so `Cargo.toml` is the single source for installer names and the app version. The release profile is `strip = "symbols"`, `lto = "thin"`, `codegen-units = 1` (smaller binary, reproducible enough, link time stays moderate). No updater and no signing material in the config (also guarded by the test). macOS minimum is 11.0.
**Rationale:** One version source cannot drift between the conf and the crates; per-user install avoids UAC for a tool that writes only to the user's profile.
**Rejected alternatives:** per-machine NSIS install (needs administrator rights, unnecessary here); MSI/WiX (extra toolchain, no benefit for a per-user tool); `tauri-action` (hides the build behind a third-party action; plain `pnpm tauri build` in our own pinned workflow stays auditable); `lto = "fat"` (much longer builds for little gain).

## 2026-11-17 – M6 release workflow: plain `pnpm tauri build`, split permissions, dry run on pull requests
**Context:** A published GitHub release has to produce the installers and attach them with checksums, without giving a build that runs third-party code a token that can write.
**Decision:** `.github/workflows/release.yml` has two jobs. `build` (matrix: Windows NSIS, macOS dmg for aarch64 and x86_64, Ubuntu 22.04 AppImage and deb) holds only `contents: read`, runs `pnpm tauri build --bundles <list> [--target <triple>]` and uploads the installers as artifacts; a glob that matches nothing fails the step and lists what the bundler produced. `publish` is the only job with `contents: write`: it downloads the artifacts, runs `tools/verify-installers.sh` (exactly the five expected files), writes `SHA256SUMS` and calls `gh release upload --clobber`. The tag, release text and inputs reach scripts only through `env:`, and `tools/check-release-version.sh` (strict `vX.Y.Z` regex, compares `Cargo.toml` and `package.json`) runs before the build. The `workflows` job in `ci.yml` runs `tools/check-workflows.sh` (pinned SHAs, no self-hosted runners, no `pull_request_target`, top-level `permissions:`, only `matrix`/`runner`/`env`/`secrets` and a few safe `github.*` values inside `run:` expressions, everything else via `env:`) and the tests of the scripts. A `pull_request` trigger limited to the packaging inputs is the dry run: it builds and uploads artifacts but never publishes. `workflow_dispatch` (with an optional `tag` to re-attach installers to an existing release) only exists once the file is on `dev`, which is why the pull-request trigger, not the manual one, is the way to try the workflow before the merge.
**Rationale:** Splitting the permissions keeps the write token away from the build and its dependencies; the explicit file list catches a bundler naming change before an incomplete release goes out. The AppImage, deb and dmg names are Tauri's documented pattern and are confirmed by the first workflow run.
**Rejected alternatives:** `tauri-action` (hides the build behind a third-party action; plain `pnpm tauri build` in our own pinned workflow stays auditable); a single job with `contents: write` (the build would run with a token that can modify releases).

## 2026-11-17 – M6 dependencies: cargo-about, and third-party notices in the installers
**Context:** The installers redistribute Rust crates, npm packages and two OFL-1.1 fonts, whose licences require the notices to travel with the binary.
**Decision:** `node tools/third-party-notices.mjs <out-file>` writes one Markdown file: the Rust part from `cargo about generate --workspace --locked --fail -o <tmp file> tools/notices/about.hbs` (`about.toml`: `accepted` mirrors the `deny.toml` allow-list, targets are the Windows, macOS and Linux triples, dev dependencies ignored) and the UI part from `pnpm licenses list --json`, limited to `@tauri-apps/api`, `@xterm/*`, `svelte` and the two `@fontsource-variable/*` fonts, each with its licence file text. It exits 1 when one of them has no licence text or is not installed (pure function `renderUiNotices`, tested through `--fixture <json>` in `tools/test-release-scripts.sh`); cargo-about itself fails on a licence outside `accepted`. cargo-about is pinned to **0.9.3** (published 2026-10-26, three weeks before use; needs `--features cli` to build its binary): the `build` job runs `cargo install --locked cargo-about@0.9.3 --features cli`, then generates `src-tauri/resources/THIRD-PARTY-NOTICES.md` before `pnpm tauri build`; `bundle.resources` ships it (guarded by `notices_are_a_bundle_resource` in `src-tauri/tests/tauri_conf.rs`). `cargo about` fetches licence files of badly packaged crates from the network, so a run takes about a minute; it hangs when its stdout is redirected on Windows (Git Bash) and refuses in PowerShell, hence `-o`.
**Committed placeholder:** `tauri-build` checks `bundle.resources` paths at compile time (a missing file makes plain `cargo check -p fernjo-app` fail with "resource path ... doesn't exist"), so `src-tauri/resources/THIRD-PARTY-NOTICES.md` is committed as a one-line placeholder and not gitignored. A local run of the script overwrites it; restore with `git checkout -- src-tauri/resources/THIRD-PARTY-NOTICES.md` and never commit the generated output.
**Rationale:** Generating at release time keeps the notices in step with `Cargo.lock` and `pnpm-lock.yaml` without a 100+ KB generated file in the history.
**Rejected alternatives:** a gitignored generated file (breaks every plain cargo build); committing the generated file (goes stale, noisy diffs); `cargo-license` or `cargo-bundle-licenses` (no per-licence template with full texts as flexible as cargo-about).
