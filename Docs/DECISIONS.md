## 2026-11-16 – M4 session IPC: raw output channel, raw input body, flow control, opener plugin
**Context:** Terminal sessions stream bytes both ways and ask the user questions while connecting. The Tauri 2 API (`tauri` 2.12.5 as in `Cargo.lock`, source read in the cargo registry before use) decides what the wire can look like.
**Decision:** **Output:** one `tauri::ipc::Channel<InvokeResponseBody>` per session carries both kinds of messages: terminal output as `InvokeResponseBody::Raw` (the JS handler receives an `ArrayBuffer`, via `new Uint8Array(...).buffer` below 1 KiB or the fetch path above it) and events as `InvokeResponseBody::Json` (the handler receives the parsed object). The UI tells them apart with `instanceof ArrayBuffer`; the JS `Channel` re-orders by the message index Tauri adds, so output and events stay in order. A typed `Channel<SomeEnum>` would force output through JSON (a number array), which is why the untyped body is used. The wire contract is documented at the top of `src-tauri/src/sessions.rs`; the Rust event type is `UiEvent` (the name `SessionEvent` is taken by `fernjo_ssh`). **Input:** `session_input` takes `tauri::ipc::Request` and reads `InvokeBody::Raw` (the webview invokes with a `Uint8Array`), the session id in the header `x-fernjo-session`; a JSON body or a missing header is `invalid_request`. Input, resizes and close go through one ordered queue per session (an unbounded `mpsc`, drained by a writer task) because separate async commands may overtake each other. **Flow control:** output is batched (16 ms or 64 KiB, in messages of at most 64 KiB); the forwarder counts sent bytes, the UI reports written bytes with `session_ack`; above 256 KiB unacknowledged it stops reading from the SSH layer until the count falls to 64 KiB (hysteresis). The SSH layer's event queue is bounded, so the server is held back by the SSH window and memory stays bounded. **Closing:** `close_session` is silent (the channel is muted first), answers every open prompt with the safe answer (reject, no secret), aborts the connect task and drops the entry. **Plan resolution** happens synchronously inside `open_session`, `resume_session` and `reconnect_session` (the spawned task needs no `AppState`); reconnect resolves again from the tree as it is, a deleted node ends as `disconnected` with "the connection no longer exists". **Opener plugin:** `tauri-plugin-opener` 2 (2.7.3 as resolved in `Cargo.lock`), registered after the dialog plugin and used only through its Rust API (`OpenerExt::opener().open_url`) in the command `open_external_url`, which accepts only absolute `http`/`https` URLs with a host (else `invalid_url`). `capabilities/default.json` stays `["core:default"]` (guarded by `src-tauri/tests/tauri_conf.rs`), so the webview cannot call the plugin's own commands or open arbitrary paths and schemes.
**Rationale:** Raw binary in both directions avoids JSON-encoding every byte; one channel keeps events and output ordered; routing the link opening through a validated Rust command keeps the webview's permissions at the minimum, like the dialog plugin.
**Rejected alternatives:** Two channels (events and output; ordering between them is lost); a typed JSON channel for output (large and slow); `Vec<u8>` as a JSON array for input (same cost, and one invoke per keystroke batch); `@tauri-apps/plugin-opener` from the webview (needs a capability and accepts any URL the UI sends); an `AppHandle`/`AppState` clone inside the connect task to resolve plans there (the plan is only needed at start, and resolving in the command reports errors straight to the caller).

## 2026-11-16 – M4 dependencies: russh, ring, RSA advisory
**Context:** M4 adds SSH sessions in the new Tauri-free crate `fernjo-ssh`. The SSH client library and its crypto backend had to be chosen, and `cargo deny check` reports `RUSTSEC-2023-0071` (Marvin Attack, RSA timing side channel) for the `rsa` crate russh uses.
**Decision:** `russh` 0.65.1 (as resolved in `Cargo.lock`) with `default-features = false` and features `flate2`, `ring`, `rsa`; `tokio` 1 with features `rt`, `net`, `time`, `sync`, `macros`, `io-util`. `russh` pins `rsa` 0.10.0-rc.18, which carries the advisory (fixed in `rsa` 0.10.0). The advisory is ignored in `deny.toml` with a reason, time-boxed by an owner decision of 2026-11-16: the ignore is removed as soon as russh depends on `rsa` >= 0.10.0 (re-check with `cargo deny check` after every russh update). `rsa` stays enabled because RSA host keys and RSA user keys are still common on real servers. **Crypto backend:** `ring`, because it builds on Windows without a C toolchain. "Pure Rust" no longer holds for the crypto backend: `ring` contains C and assembly.
**Rationale:** Dropping RSA would make fernjo unusable against many servers; the exposure is a timing side channel on RSA private-key operations (client-side signing with an RSA user key), which is accepted for now and bounded in time by the removal condition.
**Rejected alternatives:** `aws-lc-rs` as backend (needs a C toolchain / CMake on Windows); disabling the `rsa` feature (breaks RSA keys); a permanent, unconditioned ignore.

## 2026-11-15 – Vault: lost-update guard, password change and private key updates
**Context:** An unlocked vault keeps its entries in memory and writes the whole file on every change. A `vault.fernjo` delivered by a sync tool after the unlock (another device added an entry, changed the password, or a newer format arrived) would be silently overwritten, which also broke "a newer format version is refused and never overwritten".
**Decision:** `Vault::save` re-reads the file first and only writes when the file is missing (recreate) or starts with exactly the header bytes this handle last read or wrote (the body nonce changes on every save, so the header identifies the version). Anything else (another header, garbage, empty, shorter than a header, newer format) fails with the new error code `changed_on_disk` ("The vault file was changed by another device or a sync tool. Lock and unlock the vault to load the changes, then repeat your change."); entries and header in memory stay as they were. **Limit:** this is check-then-write, not a lock; a sync tool can still win the race between the check and the rename. **Password change:** the data key never rotates (keychain items must survive), so changing the master password does not re-encrypt or delete existing copies; `vault.fernjo.bak` from just before the change, backups and sync history still open with the old password and yield the data key that decrypts every later version too. This is documented in `Docs/vault-format.md` and in the change-password form; the `.bak` is not refreshed after a change. Real re-keying is not part of M3. **Private key updates:** `update_credential` with a new `privateKey` and no `passphrase` keeps the stored passphrase; `passphrase` sets or replaces it, `clearPassphrase: true` removes it (alone it keeps the key; together with a typed `passphrase` it is refused). The UI offers "Remove stored passphrase" only when editing a private key. **Threads:** the commands that run an Argon2 derivation (`vault_create`, `vault_unlock`, `vault_change_password`) are `#[tauri::command(async)]` so they run off the main thread.
**Rationale:** The guard is cheap, needs no file locking (which sync folders do not honour anyway) and turns a silent data loss into an explicit, recoverable error. Not rotating the key keeps the wrapped-key design of "Vault: wrapped data key, Argon2id, XChaCha20-Poly1305".
**Rejected alternatives:** File locks (not honoured across devices); merging two versions of the vault (needs the key and conflict rules, out of scope); refreshing `.bak` after a password change (it only hides the old copy, the sync history and backups remain); making the new key replace the passphrase silently (data loss the UI field "unchanged" did not announce).

## 2026-11-15 – Vault: secrets and known limitations of zeroisation
**Context:** Secrets must not outlive their use in memory, but the stack between the webview and the keychain contains code fernjo does not own.
**Decision:** Best-effort zeroisation only. Master passwords and entry secrets are `SecretString`/`Zeroizing` inside `fernjo-vault` and the command wrappers; the data key and derived keys are wiped after use. **Known limitations:** secrets pass through unzeroised intermediate `String`s in serde deserialisation (the internally tagged `Secret` enum buffers its content), serde_json buffer reallocations when the vault body is encoded, the Tauri IPC JSON buffer in both directions (the webview process holds the typed secret and, on reveal, the revealed one for as long as the browser engine keeps it), and the `keyring` crate and the OS keychain service. The explicit "reveal" action is the only way a secret reaches the webview, and the UI hides it again after 10 seconds or when the vault locks.
**Rationale:** A guarantee that cannot hold across serde, an IPC layer and a browser engine would be false; the goal is to keep secrets out of files, logs, snapshots and `Debug` output (enforced by tests) and to shorten their lifetime where fernjo controls the memory.
**Rejected alternatives:** A custom deserialiser that parses secrets into zeroising buffers (large code surface for a partial gain); claiming memory-safety guarantees in the docs.

## 2026-11-15 – Data folder change: restart guard
**Context:** The data folder can be changed in the app (M3). Open files, the vault mutex and the keychain id all refer to the running folder, so switching live would risk writing to two folders.
**Decision:** `apply_data_folder` validates the target (absolute, usable, not equal to or nested inside the running folder), copies `connections.json` and `vault.fernjo` only if the target has neither, writes `settings.json` last and then sets `restart_required`; the running app keeps using its old folder until `restart_app`. While the restart is pending, tree and vault commands that write refuse with `restart_required` (`ensure_writable`), so nothing is saved to the old folder after the choice; lock and unlock are allowed (they write no file). Choosing again while pending is allowed (last wins); choosing the running folder cancels the change. If the target already holds data files they are kept untouched and reported in `DataFolderInfo.existingFiles` (names, in the order `connections.json`, `vault.fernjo`); the dialog warns that this folder's data will be used instead of the current data. A failing copy rolls back the files already placed (`copy_failed`). The choice is refused with `data_dir_locked_by_env` when `FERNJO_DATA_DIR` is set, with `settings_unusable` when `settings.json` is unreadable or from a newer schema (the file is never saved over) and with `no_config_dir` when the OS has no config directory. The old folder stays intact as a backup.
**Update 2026-11-15 (M3 review):** `apply_data_folder` is a plain Rust function, not an IPC command. Only `choose_data_folder` (native picker in Rust) calls it, so the webview can never point the data folder at an arbitrary path.
**Rationale:** Copy-then-restart keeps every failure recoverable and never merges two data sets.
**Rejected alternatives:** Switching live (two data sets in flight); merging a target's existing data with the current data; moving instead of copying.

## 2026-11-15 – Master password: NFC normalisation
**Context:** The same typed password must unlock the vault on Windows, macOS and Linux, where input methods and file systems produce composed or decomposed Unicode.
**Decision:** The master password is normalised to NFC and otherwise used byte-exact (no trimming, no case folding); the minimum length of 8 counts characters after normalisation. Entry secrets (passwords, keys, passphrases) are not normalised; they are stored byte-exact. Details in `Docs/vault-format.md`.
**Rationale:** macOS keyboards and sync tools may deliver decomposed forms; NFC makes the derived key independent of that. Trimming would silently change what the user typed.
**Rejected alternatives:** NFKC (folds characters users consider distinct); no normalisation (a vault created on one OS might not open on another).

## 2026-11-15 – Vault file format
**Context:** The vault file is synced between devices by the user and must stay readable by other tools and later versions.
**Decision:** The file format (version 1: header with vault id, Argon2id parameters, salt, wrapped data key; body encrypted with the data key, whole header as AAD) is specified in `Docs/vault-format.md`, which is enough to write a reader. Parameters (128 MiB, 6 iterations, 4 lanes), load bounds, the NFC rule and the dependency versions are recorded in "M3 dependencies and vault parameters". A newer format version is reported as an unusable vault and never overwritten; saves are atomic (temp file + rename) and keep `vault.fernjo.bak`.
**Rationale:** One normative document next to the code avoids drift; decisions about why live here.
**Update 2026-11-15 (M3 review):** a save refuses to overwrite a file changed on disk since it was read (`changed_on_disk`), and changing the master password does not re-encrypt or delete older copies of the file; both are described in "Vault: lost-update guard, password change and private key updates" and in `Docs/vault-format.md`.
**Rejected alternatives:** A self-describing container such as age or JWE (larger dependency, no wrapped-data-key semantics for the keychain).

## 2026-11-15 – `settings.json` and data folder precedence
**Context:** M3 lets the owner move the data folder, so the app needs a place that says where the data folder is. That place cannot be the data folder.
**Decision:** `settings.json` (`{ "schemaVersion": 1, "dataDir"?: string }`) lives in `<OS config dir>/fernjo/` (`Location::config_dir`); `connections.json` and the vault live in `Location::data_dir`. Precedence: `FERNJO_DATA_DIR` (non-empty) > absolute `dataDir` in `settings.json` > `<OS config dir>/fernjo`. While the variable is set, `settings.json` is neither read nor written, so manual runs never touch the real config. A relative or empty `dataDir` counts as unset. If the variable is set but the OS has no config directory, `config_dir` equals `data_dir` (the override stays usable; nothing is read from it). An unreadable `settings.json` (no usable `.bak`) or one with a newer schema does not stop the app: `locate` falls back to the default folder and puts the `LoadError` in `Location::settings_error` for the app to show; the file is left untouched and callers must not save over it. A corrupt file that is recovered from `.bak` is moved to `settings.json.corrupt-<secs>` so the next save cannot copy it over the good backup. Sync-conflict copies (`sync-conflict`, `conflicted copy`, `_conflict-`) in the data folder are reported as `Notice::SyncConflicts`. The atomic write (`write_atomic`) is shared by `connections.json` and `settings.json`.
**Rejected alternatives:** Keeping `settings.json` in the data folder (circular); failing startup on a bad `settings.json` (the app would be unusable for a recoverable file).

## 2026-11-15 – M3 dependencies and vault parameters
**Context:** Milestone 3 adds `crates/fernjo-vault` (no Tauri, no `fernjo-core`). It needs a password KDF, an AEAD, a secret type, memory wiping, Unicode normalisation and a CSPRNG, all from audited crates, never home-made.
**Decision:** Dependencies (versions as resolved on 2026-11-15, see `Cargo.lock`): `argon2` 0.6.0 (Argon2id), `chacha20poly1305` 0.11.0 (XChaCha20-Poly1305, `XChaCha20Poly1305` with 24-byte nonces), `secrecy` 0.10.3 (`SecretString` for passwords), `zeroize` 1.9.1 (wiping the data key, derived keys and decrypted bodies; the `zeroize` feature is enabled on `argon2` and `chacha20poly1305`, otherwise they do not wipe the Argon2 initial hash and memory blocks or their cipher key copies), `unicode-normalization` 0.1.26 (NFC for master passwords), `getrandom` 0.4.3 (OS randomness for key, salt and nonces; called directly so no `rand_core` trait versions have to line up with the RustCrypto crates). Reused: `serde`, `serde_json`, `uuid`, `thiserror`, dev `tempfile`. `cargo deny check` stays green without new ignores. **Format:** `Docs/vault-format.md`; a random 256-bit data key is wrapped by the Argon2id-derived key, the body is encrypted with the data key and fresh 24-byte nonces on every save; the key wrap authenticates the header up to the wrapped key, the body authenticates the whole header (so a password change, which verifies the old password, picks a new salt and wrap nonce, re-wraps the unchanged data key and saves once, re-seals the small body under the same data key with a fresh nonce; the data key and the entries stay unchanged). **Master password:** at least 8 characters counted after NFC normalisation, no composition rules; NFC-normalised, otherwise used byte-exact (no trimming), so the same typed password unlocks on every OS and keyboard input method. The length rule is enforced when creating or changing a password, not when unlocking. **KDF parameters:** Argon2id with 128 MiB memory, 6 iterations, 4 lanes. Measured 0.52 s per derivation on a 6-core desktop (release build; `cargo test -p fernjo-vault --release -- --ignored --nocapture`), the "about 0.5 s" target. The values are stored in the header, so they can be raised later. The memory-heavy, few-pass choice follows the Argon2 guidance (memory is what slows GPU attackers); 128 MiB is well within every supported machine. Load bounds, applied before deriving: parallelism 1..16, iterations 1..20, memory `8 * parallelism` KiB..1 GiB. `KdfParams::TEST` (8 KiB, 1 pass, 1 lane) is the smallest accepted value and exists for tests only. The workspace `Cargo.toml` compiles `argon2` and `blake2` with `opt-level = 3` in the dev profile; unoptimised Argon2 is about 30 times slower and would make unlock take several seconds in `pnpm tauri dev` and in tests that use the default parameters.
**Also in M3:** `keyring` 4.2.0 and its OS stores (see "Vault: keychain behaviour") and `tauri-plugin-dialog` 2.8.4 (see "Data folder dialog").
**Rationale:** RustCrypto crates are the standard pure-Rust, permissively licensed implementations, with no system library on any target. XChaCha20-Poly1305 has a nonce large enough to pick at random on every save without a counter, which matters for a file that is synced between devices.
**Rejected alternatives:** `rand` as the randomness source (an extra dependency and trait-version coupling for filling a few byte arrays); AES-GCM (12-byte nonces make random nonces on a long-lived synced file less comfortable); scrypt or PBKDF2 (Argon2id is the current recommendation and resists GPUs better); encrypting the body directly with the password-derived key (a password change would re-encrypt everything and the keychain could not hold a password-independent key).

## 2026-11-15 – M2 dependencies
**Context:** The connection tree needs serialisation, ids, errors, a config directory, a single-instance guard and the Tauri JS API.
**Decision:** Rust (`fernjo-core`): `serde` 1.0.229 and `serde_json` 1.0.154 (JSON), `uuid` 1.29.2 (v4 ids), `thiserror` 2.0.21 (error types), `directories` 6.0.0 (OS config directory), dev-only `tempfile` 3.27.0. `src-tauri`: `fernjo-core` (path) and `tauri-plugin-single-instance` 2.5.5, which on Linux pulls in `zbus` (D-Bus) and with it three "unmaintained" advisories (`RUSTSEC-2026-0370`, `-0371`, `-0372`: `zvariant`, `zbus_names`, `zvariant_derive`); they are listed in `deny.toml` with a reason because no upgrade exists. UI: `@tauri-apps/api` 2.12.4. Versions are the ones `Cargo.lock` / `pnpm-lock.yaml` resolved on 2026-11-15; `cargo deny check` is green.
**Rationale:** All are the standard crates for their job, permissively licensed, and already in Tauri's own dependency tree or widely used. The single-instance plugin is the supported Tauri way to focus the running window.
**Rejected alternatives:** A home-made lock file or named pipe for single instance (platform-specific code we would have to test three times); `confy`/`config` crates (we write one fixed file with our own atomic-write rules); `directories`' `ProjectDirs` (adds a `config` subfolder on Windows, see the data-folder entry).

## 2026-11-15 – IPC content security policy
**Context:** M0 left a follow-up (entry "Webview hardening from day one"): the CSP had no `connect-src` for Tauri IPC, and the config test forbade the substring `http:`. M2 adds the first Tauri commands.
**Decision:** The CSP gains `connect-src ipc: http://ipc.localhost` (everything else unchanged: `default-src 'self'`, no `unsafe-eval`). `src-tauri/tests/tauri_conf.rs` now requires that exact `connect-src`, rejects the token `*` and `unsafe-eval`, and allows no `http:`/`https:` token other than `http://ipc.localhost`. Capabilities stay `core:default`. Verified: with this CSP the running app loads the tree through the commands (no IPC blocked).
**Rationale:** Tauri 2 sends commands over `ipc:` (and `http://ipc.localhost` on Windows/Android); without the entry a strict `default-src` blocks them. The relaxed test still forbids every external origin.
**Rejected alternatives:** Dropping the CSP or using `connect-src *`; the custom-protocol-only workaround (not available on all platforms).

## 2026-11-15 – Pointer-based drag and drop in the tree
**Context:** M2 needs moving nodes by drag and drop in a nested tree with three drop zones per folder (before, inside, after). The owner's Linux setup is Wayland with WebKitGTK.
**Decision:** The tree is dragged with pointer events (`pointerdown`/`pointermove`/`pointerup`, pointer capture once a 4 px threshold is crossed). A pure function (`ui/src/lib/drop-target.ts`, `dropPosition` and `resolveDrop`) maps the pointer to a drop (new parent and index, counted after the dragged node is removed, the same convention as the Rust `move_node`); a DOM-free `DragController` holds the state machine. Rust validates every move; the only call is `move_node`. Dragging is off while a filter is active or a rename is open; Escape cancels.
**Rationale:** Native HTML5 drag and drop needs `dragDropEnabled: false` in the Tauri window and is the least reliable on WebKitGTK/Wayland; the pointer approach behaves the same in all three webviews and is unit-testable without a browser.
**Rejected alternatives:** Native HTML5 drag and drop; a Svelte drag-and-drop library (not built for nested trees with three drop zones, extra dependency).

## 2026-11-15 – `connections.json`: format, location, write strategy
**Context:** M2 persists the connection tree; later milestones add settings (credential reference in M3, RDP in M7) and import (M5). The file must survive crashes and newer app versions, and must never hold a secret.
**Decision:** The tree lives in Rust (`fernjo-core`, a pure `Tree` plus a `Store` that saves after every mutation); every mutating Tauri command returns the full new snapshot and the UI renders snapshots (the UI keeps only selection, expansion, filter and drag state). Delete asks for confirmation and is final; `connections.json.bak` is the only safety net. **Format:** `connections.json`, pretty-printed UTF-8 JSON, `{ "schemaVersion": 1, "children": [ … ] }`, nodes nested: `{ "id" (UUID v4), "type": "folder"|"connection", "name", "description", "settings": { "username", "port", "keepaliveSecs" } (omitted keys = inherit), and either "children": [ … ] or "protocol": "ssh"|"rdp", "host" }`. Order is the position in `children`. No credential field exists. Inheritable in M2: username, port, keepalive; effective value = nearest value from the node up through its folders, then the default (SSH 22, RDP 3389, keepalive 30 s with 0 = off, no username; a folder's port has no default). **Location:** `<OS config dir>/fernjo/` (`%APPDATA%\fernjo`, `~/Library/Application Support/fernjo`, `~/.config/fernjo`), overridden by the environment variable `FERNJO_DATA_DIR` (tests, the sample-tree generator). **Write:** temp file in the same folder, `sync_all`, copy the current file to `connections.json.bak`, rename the temp file over the target; a failed save leaves memory unchanged (the mutation is applied to a copy first). **Load:** a missing file is an empty tree (created by the first mutation); a `schemaVersion` newer than the app is refused and never overwritten; an unreadable file falls back to `.bak` after being renamed to `connections.json.corrupt-<unix seconds>` (so a later save cannot replace the good `.bak` with garbage) and the UI shows a notice; if both are unreadable the app starts in an error state and writes nothing. Migration is a chain of version N → N+1 functions (empty for now, tested). **Update 2026-11-15 (M3, schema 2):** `schemaVersion` is now 2 and `settings` gains an optional, inheritable `credential` (vault entry UUID, omitted = inherit; resolved like `port`, no default; the core never knows the vault, so the id may dangle). The 1 → 2 migration step is a no-op that exists only so older builds refuse the file (they would drop `credential` on their next save); a version-1 file loads and is written as version 2 on the next save (the version-1 bytes stay in `.bak`), version 3 is refused as a newer schema. The "No credential field exists" sentence above applies to schema 1 only.
**Rationale:** Rust ownership keeps validity and inheritance in one tested place, and a snapshot per mutation (~170 KB at 500 connections) is simple and cannot drift. The write sequence never leaves a half-written main file; the load rules never destroy data the user might still want.
**Rejected alternatives:** UI-owned tree pushed to Rust (logic would drift into TypeScript); diff or event streams (complexity with no benefit at this size); instant delete with an undo toast (needs an undo history in the core); `directories`' `ProjectDirs` layout (adds a `config` subfolder on Windows); renaming the temp file over the old one without a `.bak` copy.

## 2026-11-15 – UI tokens, theming and bundled fonts
**Context:** M2–M6 build the real UI; it needs a stable token interface that renders in WebView2, WKWebView and WebKitGTK 4.1 (Ubuntu 22.04) under a strict CSP.
**Decision:** `ui/src/styles/tokens.css` is the token interface (names only grow; renames need a new entry here). Light values in `:root`; dark values in `:root[data-theme="dark"]` and in `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }` with identical contents, so M6's theme setting only sets `data-theme` on `<html>`. Colours are `#rrggbb`/`#rrggbbaa`; modern colour functions, nesting, `@layer`, `:has()` and container queries are not used. `ui/src/styles/tokens.test.ts` guards names, parity, hex format, banned CSS and WCAG contrast pairs (Vitest runs with `css: true` so `?raw` imports work). Fonts are bundled from npm, pinned: `@fontsource-variable/hanken-grotesk` 5.3.0 and `@fontsource-variable/red-hat-mono` 5.3.0 (both OFL-1.1, about 99 KB woff2 in total, normal style only). Vite asset inlining is off (`assetsInlineLimit: 0`) because the CSP blocks `data:` fonts. The terminal's minimum contrast (4.5, `--terminal-min-contrast`) is applied by xterm.js `minimumContrastRatio` in M4 instead of bending the palette.
**Rationale:** The webview with the oldest engine sets the rules; tests keep the rules from eroding; bundled fonts keep the CSP strict and work offline.
**Rejected alternatives:** `oklch`/`light-dark()` (unsupported in WebKitGTK 4.1); Google Fonts at runtime (blocked by the CSP and a privacy leak); loosening the CSP for `data:` fonts; system font stacks only (would make the look differ per OS).

## 2026-11-15 – CI toolchain: plain rustup, UI build first, hosted Ubuntu only; gitleaks CLI for the history scan
**Context:** `.github/workflows/ci.yml` must install the pinned Rust toolchain, build a Tauri crate that embeds the frontend; separately, the full git history must be scanned for secrets once before the repo goes public; the cargo-deny job runs with the default advisory scope.
**Decision:** The pinned toolchain is installed with `rustup toolchain install` (rustup 1.28+ no longer installs on `rustup show`), not a third-party toolchain action. The `rust` CI job needs no UI build: plain cargo builds are Tauri dev builds and do not embed `ui/dist`; only `pnpm tauri build` embeds it and runs `pnpm ui:build` itself (`beforeBuildCommand`), which the `tauri-build` job covers. CI runs on `ubuntu-latest` only; the Ubuntu 22.04 minimum is checked when packaging (M6). The history scan is a one-off run of the gitleaks CLI, done locally before the repo goes public (M0 release task, "Scan the full git history for secrets"), not a CI job: `ci.yml` has no gitleaks step. The CLI is used instead of `gitleaks-action`, which needs a licence for organisations. Known gap: cargo-deny's unsound/unmaintained checks default to workspace direct dependencies only, so `RUSTSEC-2024-0429` (`glib` 0.18.5 unsound, via Tauri's GTK3 stack) is only reported with `unsound = "all"`; revisit when Tauri leaves GTK3.
**Rationale:** Fewer third-party actions to pin and trust; the `rust` job stays free of Node tooling; hosted minutes are free for a public repo and one Linux job covers the code paths until packaging.
**Rejected alternatives:** A third-party toolchain action (extra supply-chain surface); `gitleaks-action` (licence); an OS matrix in M0 (cost without a packaging step to test); enabling `unsound = "all"` now (would fail on a Tauri-internal advisory we cannot fix).

Follow-up closed in: IPC content security policy (M2).
**Rationale:** Tightening a CSP and capability set later is harder than starting strict; the tests keep them from drifting.
**Rejected alternatives:** `csp: null` until needed; broad default capabilities.

## 2026-11-15 – cargo-deny: licence allow-list and advisory ignores
**Context:** M0 adds a `cargo-deny` CI job (advisories, bans, licences, sources) that must be green on the workspace including Tauri's dependency tree (cargo-deny 0.20.2, run with `--all-features`; the graph covers all platforms, so Linux-only crates are checked too).
**Decision:** `deny.toml` allows only `MIT`, `Apache-2.0`, `Apache-2.0 WITH LLVM-exception`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `Zlib`, `Unicode-3.0`, `CC0-1.0`, `MPL-2.0`; no licence was added beyond this starting list (the first run reported no licence violations). Sources are crates.io only (unknown registry and git denied); duplicate versions only warn. One advisory is ignored: `RUSTSEC-2024-0370` (`proc-macro-error` unmaintained, pulled in by `glib-macros` through Tauri's Linux GTK3 stack; no safe upgrade exists). Remove the ignore when Tauri moves off GTK3 (or `glib-macros` drops `proc-macro-error`); `cargo deny check` will then report the entry as unused, as a *warning* (not an error), so look for it in the output after Tauri upgrades. Wildcard dependencies are not allowed (default `warn` is not loosened) and the licence confidence threshold stays at its default.
**Rationale:** The allow-list is limited to permissive licences and MPL-2.0 (weak copyleft), all compatible with distribution under `MIT OR Apache-2.0`. The ignore is a single, id-specific entry with a reason: the crate is a build-time proc macro we cannot replace, and it is an unmaintained notice, not a vulnerability.
**Rejected alternatives:** Disabling the unmaintained check (`unmaintained = "none"`) or blanket-ignoring advisories (would hide future findings); allowing licences speculatively (every addition should be driven by a real finding); skipping crates in the licence check.

**Context:** The owner wants fernjo open source and left the choice of licence open.
**Decision:** Dual licence `MIT OR Apache-2.0`.
**Rationale:** Rust ecosystem convention, compatible with all planned dependencies (russh, IronRDP, Tauri, xterm.js), and Apache-2.0 adds a patent grant.
**Rejected alternatives:** GPL-3.0 (would keep forks open, but more friction and not needed for a personal tool); proprietary (the owner wants open source).

## 2026-11-15 – Public repo, CI only on GitHub-hosted runners
**Context:** Tauri on Linux needs WebKitGTK system packages; the org's self-hosted runner (`dotnet-linux`) has no root. Release builds need macOS and Windows machines. Hosted-runner minutes cost money on private repos.
**Decision:** The repo is made public in M0, and all CI, including the `roadmap` job, runs on GitHub-hosted runners. Repo security is switched on: secret scanning with push protection, Dependabot alerts and updates, CodeQL, private vulnerability reporting, `cargo-deny`, and approval for workflows from outside contributors.
**Rationale:** Free hosted minutes for public repos, all three OSes available. Self-hosted runners must never run workflows of a public repo, because fork PRs could execute code on them.

## 2026-11-15 – Vault: wrapped data key, Argon2id, XChaCha20-Poly1305
**Context:** Credentials must be stored encrypted, the vault file may be synced between devices by the user, and "unlock automatically on this device" uses the OS keychain.
**Decision:** A random 256-bit data key encrypts the whole vault file; the master password derives (Argon2id) a key that wraps the data key. The OS keychain stores the data key. RustCrypto crates only.
**Rationale:** Changing the master password only re-wraps the data key, so keychain entries on other synced devices stay valid; no home-made crypto.
**Update 2026-11-15 (M3):** The statement above is imprecise: a password change re-wraps the data key and re-saves the file, and the body is re-sealed with a fresh nonce because the whole header is its AAD (see "M3 dependencies and vault parameters"). The data key and the entries stay unchanged, so keychain entries stay valid.
**Rejected alternatives:** Storing the password-derived key in the keychain (invalidated on every password change); OS keychain as the only store (does not sync across OSes, no portable backup).

## 2026-11-15 – Vault: keychain behaviour
**Context:** "Unlock automatically on this device" needs the data key in the OS keychain, without a system C library on Linux.
**Decision:** `keyring` 4.2.0 (with `keyring-core` 1.0.1) with its default `v1` feature, which selects per OS: `windows-native-keyring-store` 1.1.0 (Credential Manager), `apple-native-keyring-store` (macOS Keychain) and `zbus-secret-service-keyring-store` 1.0.1 (Secret Service over `zbus`, no libdbus; `cargo tree -p fernjo-vault --target x86_64-unknown-linux-gnu` shows no `dbus` crate). Item: service `fernjo`, user = vault id, secret = the 32 raw key bytes (`DataKey`, wiped after use). Auto-unlock (`try_auto_unlock`) never prompts: a missing item gives `NoKey`, a keychain error `Unavailable`, a key that fails authentication (`tampered`) deletes the item (`StaleKeyRemoved`); the vault stays locked in all of these and the UI falls back to the master password. A master password change keeps the data key, so stored keys stay valid. **Trade-off:** any `tampered` result from `unlock_with_key` deletes the keychain item, including the case of a corrupted or half-synced vault body with a valid key; the user then has to unlock with the master password and enable auto-unlock again. **Other readers of the keychain:** a second launch of the app (single-instance) also runs the auto-unlock attempt before it exits, so it reads the keychain, may delete a stale item and, on macOS, may trigger a keychain prompt. `lock` never touches the keychain (the lock lasts until the next start); `set_auto_unlock(true)` surfaces a keychain error (`keychain_unavailable`), while a keychain failure on unlock or create is ignored and only leaves `autoUnlock` false.
**Update 2026-11-15 (M3 review):** because the data key never rotates, changing the master password does not lock out the old password for older copies of the vault file (`vault.fernjo.bak`, backups, sync history): they still open with the old password and the key they yield decrypts every later version. Real re-keying is not in M3. Unticking "Unlock automatically on this device" in the lock note now removes the keychain item after a successful unlock (the UI calls `vault_set_auto_unlock(false)`; `vault_unlock` with `remember: false` itself never deletes the item).
**Threat model:** With auto-unlock on, the data key is readable by anything running as the same OS user, so such a process can open the vault. Auto-unlock is therefore an explicit opt-in per device; the master password protects the vault file when it is copied or synced elsewhere.
**Rejected alternatives:** `dbus-secret-service` / `linux-keyutils` stores (libdbus or kernel keyring without persistence); storing the password-derived key (see above).

## 2026-11-15 – SSH via russh, RDP via IronRDP
**Context:** The core must be Rust; SSH is used more than RDP.
**Decision:** russh (tokio) for SSH; IronRDP for RDP, rendered through a framebuffer streamed to a canvas. The RDP milestone starts with a measured spike; a native render surface is the fallback (its own milestone if needed).
**Rationale:** Both are pure Rust and actively maintained; IronRDP supports TLS, NLA/CredSSP and clipboard.
**Rejected alternatives:** FreeRDP via FFI (C dependency, kept as fallback if IronRDP fails for protocol reasons); launching the OS RDP client (none on macOS/Linux, breaks the one-window idea); libssh2 bindings (C dependency).

## 2026-11-15 – UI: Tauri 2 + Svelte 5 + xterm.js
**Context:** fernjo needs a high-quality terminal (main use is SSH), a modern UI (the reason for the project) and RDP rendering, on three OSes.
**Decision:** Tauri 2 shell, Svelte 5 + TypeScript frontend, xterm.js for the terminal. All logic stays in Rust crates that do not depend on Tauri.
**Rationale:** xterm.js is a mature terminal (used by VS Code); web UI makes design iteration cheap. RDP via canvas is the accepted risk, checked by a spike.
**Rejected alternatives:** egui/Iced + alacritty_terminal (all Rust, best RDP, but immature terminal widget and harder to make look modern); Slint (no terminal widget); Electron (heavy, non-Rust core); Qt bindings (awkward in Rust).

## 2026-11-15 – Data folder dialog: tauri-plugin-dialog (Rust API only)
**Context:** M3 lets the user pick the data folder; the native folder picker must open from Rust and the webview must gain no new permissions.
**Decision:** `tauri-plugin-dialog` 2.8.4 (`tauri-plugin-dialog = "2"`), registered after the single-instance plugin and used only through its Rust API (`DialogExt::file().blocking_pick_folder()` on a `spawn_blocking` worker). No JS permission is added: `capabilities/default.json` stays `["core:default"]` (guarded by `src-tauri/tests/tauri_conf.rs`), so the webview cannot call the plugin's own commands. `apply_data_folder` copies `connections.json` and `vault.fernjo` only into a folder that has neither of them, writes `settings.json` last and then sets `restart_required`; the running app keeps its old folder until `restart_app`.
**Update 2026-11-15 (M3 review):** `apply_data_folder` is not registered as an IPC command; the path only ever comes from the native picker.
**Rationale:** The picker needs no frontend code, and the dialog result goes through the same validated Rust path as any other choice.
**Rejected alternatives:** `@tauri-apps/plugin-dialog` from the webview (needs a capability, and the path would come from the UI); a text field for the path (error-prone); moving files instead of copying them (the old folder stays intact as backup).
