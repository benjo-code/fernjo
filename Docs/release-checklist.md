# Release checklist

This file has three parts: the reusable checklist for every release (next), the readiness result for v0.1.0, and the v0.1.0 security review with its evidence (plus one result section per later release). A release happens only on the owner's explicit instruction (`CLAUDE.md`, "Releases" and "Collaboration"); this file prepares the decision and never performs it.

## Reusable checklist (every release)

Run it on the exact commit the release will be cut from and write the result into a new "vX.Y.Z result" section.

1. **Version and metadata.** `Cargo.toml` `[workspace.package] version`, `package.json` `version` and the new `CHANGELOG.md` heading all name the release. `bash tools/check-release-version.sh vX.Y.Z` passes (it also checks the hub image tag pinned in `crates/fernjo-hub/deploy/compose.yaml` and `fernjo-hub.container`; before the release branch it fails only because Cargo.toml and package.json still say the old version). `cargo metadata --locked` and `pnpm install --frozen-lockfile` succeed (lock files current). `LICENSE-MIT`, `LICENSE-APACHE` exist; the release workflow generates `THIRD-PARTY-NOTICES.md` into `src-tauri/resources/` and every installer of the dry run contains it.
2. **Documentation matches the app.** Every claim in `README.md` (features, SSH sign-in order, shortcut table against `ui/src/lib/shortcuts.ts`, install section, privacy statement), `SECURITY.md` and the issue templates is true for this version; `[Unreleased]` names the milestones it contains. `dotnet run tools/roadmap.cs -- check` is valid.
3. **Build and test evidence on that commit.** `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, `pnpm test`, `pnpm lint`, `cargo deny check`, `bash tools/check-workflows.sh`. The SSH integration tests count only with the throwaway container (`eval "$(tools/ssh-test-server.sh start)"`, run, `tools/ssh-test-server.sh stop`) or through the CI `rust` job, which starts it and fails when it is missing. `gh pr checks <pr>` is fully green, including the CodeQL result check and the `release.yml` dry run (five installers, smoke tests, `SHA256SUMS`).
4. **Security review.** Repeat the section "v0.1.0 security review" for what changed since the last release (secrets, webview and IPC surface, release-binary hygiene, network behaviour, data at rest, SSH algorithms, supply chain, pipeline); `gh api repos/benjo-code/fernjo/code-scanning/alerts?state=open` is empty, `/security-review` of the diff is run, gitleaks over the history is clean.
5. **Known gaps table.** List every open manual check, every unfixed finding and every unverified claim with a disposition (blocker, accepted for this release, after release). An unverified claim is never shown as verified.
6. **Attach-step rehearsal: retired (2026-11-25).** Since the `v*` tag ruleset a pushed `v0.0.0` cannot be deleted again, and `release.yml` now publishes the draft it attaches to (immutable releases, `Docs/DECISIONS.md` "M11: immutable releases, draft then publish"), so the rehearsal below would leave a public, permanent `v0.0.0` release. The `publish` job's first run in the draft form is the release itself; every step before "Publish the release" leaves only a draft, which is retried with "Re-run failed jobs" (`gh run rerun <run id> --failed`, reuses the built installers for 7 days), with `gh workflow run release.yml --ref vX.Y.Z` (builds again), or deleted. The old text, kept for the record: `workflow_dispatch` with `tag` attaches to an *existing* release, and the workflow checks out that tag and runs `tools/check-release-version.sh` on it, so the tag must exist and must equal the version in the files. A draft release does not create its tag until it is published, and the version check accepts only `[v]MAJOR.MINOR.PATCH` (no `-rehearsal` suffix, no `-rc.1`). While the files still say `0.0.0` the only tag that passes is `v0.0.0`: `git tag v0.0.0 origin/dev && git push origin v0.0.0`, then `gh release create v0.0.0 --draft --verify-tag --title rehearsal --notes rehearsal`, then `gh workflow run release.yml --ref dev -f tag=v0.0.0`; check that the draft holds the five installers and `SHA256SUMS`, then delete the draft and the remote tag (`gh release delete v0.0.0 --cleanup-tag --yes`) and the local one (`git tag -d v0.0.0`). Needs the workflow on `dev` (the default branch) and the owner's go-ahead; run it before the version files are bumped. The pushed tag `v0.0.0` (and the draft's name) is publicly visible on this public repo until the cleanup step has run, so do the cleanup right after checking the assets. Run for v0.1.0's predecessor state on 2026-11-18 (see "Step 5"): the dispatch run checked out the tag, `publish` ran, `gh release upload "$TAG"` found the draft by tag (the REST endpoint `releases/tags/{tag}` returns published releases only, so `gh` does fall back to listing), and the cleanup left no tag and no release behind.
7. **Verdict.** One go / no-go line per area (security review, installers, docs, performance, repo settings) and an overall line, or the list of blockers.
8. **Release binaries carry no build paths.** The dry run's step "Check the binary for build paths" (`tools/check-no-build-paths.sh`) is green in all four app jobs of the release commit's pull request; record the run URL.
9. **Release (only on the owner's instruction, `CLAUDE.md` "Releases").** Branch `release/vX.Y.Z` from `dev`, bump the versions in `Cargo.toml` (a build then refreshes `Cargo.lock`; commit it), `package.json` and the hub image tag in `crates/fernjo-hub/deploy/compose.yaml` and `fernjo-hub.container`, turn `[Unreleased]` into `[X.Y.Z] - YYYY-MM-DD` and add an empty `[Unreleased]`; PR to `main` (merge commit); push the tag `vX.Y.Z` on `origin/main` (the push runs `release.yml`) and right after it create the draft with `gh release create vX.Y.Z --draft --verify-tag --title "vX.Y.Z" --notes "<CHANGELOG section>"` (exact commands in `CLAUDE.md` "Releases"); `release.yml` builds, smoke-tests, attests and attaches the installers and `SHA256SUMS` to the draft and publishes it (never publish the draft by hand: an immutable published release takes no files); check the published files and `gh attestation verify` on one installer; check the hub image once the run is green: `docker buildx imagetools inspect ghcr.io/benjo-code/fernjo-hub:X.Y.Z` lists `linux/amd64` and `linux/arm64`, the tags `X.Y` and `latest` show the same digest, and `gh attestation verify oci://ghcr.io/benjo-code/fernjo-hub:X.Y.Z --repo benjo-code/fernjo --signer-workflow benjo-code/fernjo/.github/workflows/release.yml --source-ref refs/tags/vX.Y.Z` passes; merge `main` back into `dev` (merge commit).

### Update check against a local test feed (optional, for owner check 5)

`tools/update-test.conf.json` is merged into the configuration of two local debug builds. It points the updater at `http://127.0.0.1:8765/latest.json` (8765 is a placeholder port: change it in that file and in the steps below together), pins the published TEST key of `src-tauri/tests/fixtures/update-test-key/` and sets `dangerousInsecureTransportProtocol`; `requireSignedVersion` stays on. No release uses it (`update_test_config_is_never_used_by_a_release` in `src-tauri/tests/tauri_conf.rs`).

Before you start:

- Such a build accepts any update signed with a key whose private half is public. Never hand it to anyone, and remove it afterwards.
- It has the identifier and the data folder of the real fernjo. Close the installed app, back up the data folder (`<OS config dir>/fernjo`, `%APPDATA%\fernjo` on Windows, or the folder chosen in Settings) and note the SHA-256 of `connections.json`, `vault.fernjo` and `settings.json`. On Windows the test build replaces the installed fernjo. Do not rely on `FERNJO_DATA_DIR` here: it switches the automatic check off, and the restarted app may not inherit it.

Run the commands from the repository root (Git Bash on Windows). `<feed>` is an empty folder outside the repository, given as an absolute path; `<NEW>` is the version in the root `Cargo.toml`.

| OS | `<bundle>` | Built below `target/debug/bundle/` | Platform key |
|---|---|---|---|
| Windows | `nsis` | `nsis/fernjo_<version>_x64-setup.exe` | `windows-x86_64` |
| Linux | `appimage` | `appimage/fernjo_<version>_amd64.AppImage` | `linux-x86_64` |
| macOS | `app` | `macos/fernjo.app` | `darwin-aarch64` or `darwin-x86_64` |

1. **Old version.** Set `version` under `[workspace.package]` in the root `Cargo.toml` to `0.0.1`, run `pnpm tauri build --debug --config tools/update-test.conf.json --bundles <bundle>`, move the result to a third folder, outside the repository and not `<feed>` (the next build overwrites `fernjo.app`), then `git checkout -- Cargo.toml Cargo.lock`.
2. **New version.** Run the same build command without the edit and put the update file into `<feed>`: the setup or the AppImage as it is; on macOS `COPYFILE_DISABLE=1 tar -C target/debug/bundle/macos -czf <feed>/fernjo_<NEW>_<aarch64 or x64>.app.tar.gz fernjo.app`.
3. **Sign** it with the test key (empty password):

       env -u TAURI_SIGNING_PRIVATE_KEY -u TAURI_SIGNING_PRIVATE_KEY_PASSWORD \
         pnpm tauri signer sign -f src-tauri/tests/fixtures/update-test-key/test-only.privkey -p "" \
         --app-version <NEW> <feed>/<file>

       {
         "version": "<NEW>",
         "notes": "Update test",
         "platforms": {
           "<platform key>": {
             "signature": "<the whole content of <file>.sig>",
             "url": "http://127.0.0.1:8765/<file>"
           }
         }
       }

### Known residual limits

The feed body is read without a size cap by the plugin (bounded by the 15 s check timeout and the pinned HTTPS endpoint); the download cap overshoots by one read slice; `sign` trusts the output of `build` including its caches (existing pipeline behaviour); a macOS or Linux install that returns instead of exiting and a confirm that arrives after the state left Ready (for example because a check found a newer version while the dialog was open) are rare races; a quit on macOS through the menu (Cmd+Q) is likely held back by neither the close confirmation nor a running install (read in the dependency sources, roadmap backlog); all noted in `Docs/DECISIONS.md`.
