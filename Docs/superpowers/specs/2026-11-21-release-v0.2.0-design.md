# Release v0.2.0: design

Date: 2026-11-21 · Status: awaiting the owner's approval in chat

## Intent

Publish v0.2.0, "RDP" (milestone 8): RDP connections open as tabs next to SSH (TLS and network level authentication, certificate pinning, a canvas that follows the tab, keyboard and mouse, text clipboard, in-app full screen, inheritable RDP settings, `connections.json` schema 3). It repeats the sequence of v0.1.0 and v0.1.1 (`2026-11-20-release-v0.1.1-design.md`), so the owner gets RDP in installers instead of dev builds.

## Goals

- `v0.2.0` exists as a GitHub release on `main` with five installers and `SHA256SUMS`, built and smoke-tested by `release.yml`.
- `main` and `dev` keep their common history (merge commits only).
- Every claim in README, CHANGELOG, the roadmap and the checklist is true once the release exists; anything unverified is named as such.

## Non-goals

- No new features or fixes. Anything found goes to the backlog, unless it is a blocker (then the stop rule applies).
- No code signing, no auto-update, no change to `release.yml`.
- The M8 items the owner's run did not cover (Windows Server, a release build, per-web-view clipboard details, two unexplained `spike_bench` lines) are not run by the plan; they are listed as known gaps, except the release-build check, which is offered to the owner as an optional gate (see Design, step 6).
- `spike/m08-rdp-canvas` and the open Dependabot PR #3 are not touched.

## Anti-goals

- A release with a red check, an alert that is new to `main`, an unfixed High or Medium security finding, or a version mismatch between tag, `Cargo.toml`, `Cargo.lock` and `package.json`.
- A half-published state repaired by deleting and recreating releases or tags without the owner's decision.
- Describing "ran with `pnpm tauri dev`" as "ran in the installer", or a waived or unrun check as verified.

## Constraints

- `CLAUDE.md` "Git & branches" and "Releases": branch `release/vX.Y.Z` from `dev`; PRs to `main` and the back-merge use "Create a merge commit"; no force push, no `--no-verify`, no deleting branches. A merge to `main` and a release happen only on the owner's explicit instruction; **this time the instruction is not given in advance** (v0.1.1 had one). The plan stops before the PR to `main` and asks.
- `tools/check-release-version.sh` accepts only `[v]MAJOR.MINOR.PATCH`.
- `main` requires `roadmap`, `rust`, `ui`, `tauri-build`, `cargo-deny`, `workflows` and an up-to-date branch.
- The development machine has no usable WebView2 runtime, so neither `pnpm tauri build` nor the app runs here; installers exist only through the CI dry run of the release PR.
- CodeQL alerts are dismissed only on the owner's explicit instruction. Six are open on `dev` (#122 to #127, rule `rust/hard-coded-cryptographic-value`, made-up sentinel passwords in test code of `fernjo-rdp` and `src-tauri/src/sessions/rdp/tests.rs`, created 2026-11-21). They are new relative to `main`, so the release PR's CodeQL result check will report them. Same situation as alerts 106 to 118 before v0.1.0, which the owner had dismissed as "used in tests".

## Approaches

1. **Checklist step 9 sequence, as for v0.1.0 and v0.1.1 (chosen):** `release/v0.2.0` from `dev`, bump and docs, gate, security review, PR to `main` (merge commit), `gh release create v0.2.0 --target main`, back-merge, evidence PR.
2. Squash into `main`: rejected, `CLAUDE.md` forbids it.
3. Release from `dev`: rejected, `main` holds only published states.
4. Wait for the Windows Server and release-build checks first: not chosen as a default, because the owner closed M8 on 2026-11-21 knowing they were open; but the release-build check is cheap after the dry run and is offered (step 6).

## Design

1. **Preconditions.** Push CI of `dev` at `09d08b7` (`CI`, `CodeQL`, `Roadmap`) is green (it was on 2026-11-21); working tree clean.
2. **Release branch and edits.** `release/v0.2.0` from `dev`. `[workspace.package] version` and `package.json` to `0.2.0`, with the refreshed `Cargo.lock` (six workspace crates including `fernjo-rdp`). `CHANGELOG.md`: `[Unreleased]` becomes `[0.2.0] - <release date>` naming M8, with a new empty `[Unreleased]`; the RDP entry says the owner ran it from `pnpm tauri dev` builds. README: the status line, the "In the next release" block (now shipped), the privacy paragraph ("no network connections except the SSH sessions you open" is false once RDP exists) and anything else M8 made untrue. `SECURITY.md` checked for the same. Roadmap: release `0.2.0` done with its date, `generate`.
3. **Checklist on that commit.** Gate commands as for v0.1.1 plus the live RDP tests noted as skipped locally; a section "v0.2.0 result" in `Docs/release-checklist.md`.
4. **Security review of `v0.1.1..HEAD`** (90 files, about 10,000 added lines, mostly `fernjo-rdp` and the session glue): `/security-review`, plus a fresh read-only reviewer with the "v0.1.0 security review" areas and the RDP-specific ones as the brief: certificate decision and pinning (`cert_store.rs`, `connect.rs`), what a hostile server can make the client do (bitmap sizes, clipboard length, resize), secrets in `ConnectParams` and `Debug`, the three RDP commands in `no_response_contains_a_secret`, CSP and webview surface unchanged, the `rsa` release-candidate advisory ignore, new dependency licences and advisories, gitleaks over the history.
5. **PR to `main`.** Needs the owner's go (see Constraints). Alerts #122 to #127 must be dismissed first, on the owner's say, otherwise the CodeQL check is red and the plan stops. All required checks and the `release.yml` dry run green, then merge with a merge commit.
6. **Optional owner gate: installer check.** After the dry run, the Windows installer artifact (`installers-windows`) can be installed and tried against the owner's Windows 11 host: connect, certificate prompt, typing, resize, clipboard, full screen. It is the one thing nobody has seen: M8 ran only from `pnpm tauri dev`, and the CSP and the embedded UI only apply in a release build (the RDP canvas uses `putImageData`, which the CSP does not restrict, but no run shows it). The owner decides before step 7; the result is recorded either way (run, or "not run, accepted").
7. **Release, back-merge, evidence.** `gh release create v0.2.0 --target main --title "v0.2.0" --notes-file <CHANGELOG section>`, watch `release.yml`, check the five installers and `SHA256SUMS`, then PR `main` into `dev` (merge commit), then a docs PR with the evidence.

## Stop rule

Stop and report, without a workaround, when: a gate command or CI check is red; CodeQL reports an alert that is not one of #122 to #127 or that cannot be dismissed on the owner's word; the security review finds a High or Medium issue that is not already fixed; `git status` or a diff shows something unexpected; the release workflow fails or the attached files are wrong. No deleting or re-creating of the release or the tag without the owner's decision.

## Left to the builder

Exact wording of README, CHANGELOG and checklist text; dispositions of new Low findings (accept with a reason, or backlog); whether the evidence PR is needed once everything is recorded.
