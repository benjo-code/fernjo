# Release v0.4.0: design

Date: 2026-11-27 · Status: approved in chat by the owner ("approved", 2026-11-27); the irreversible steps still need their own go (see Constraints)

## Intent

Publish v0.4.0, "Automatic updates" (milestones 13 and 14): the app checks for a newer version and updates itself with one click, after the security check of the update path. Installing this version by hand is the last manual update. The M14 verdict is go ("v0.4.0 readiness" in `Docs/release-checklist.md`). The sequence is that of v0.3.0 (`2026-11-25-release-v0.3.0-design.md`) plus what M13 added to `release.yml`: the update files are signed, the signatures checked and `latest.json` written, all for the first time.

## Goals

- `v0.4.0` is a published GitHub release on `main` with exactly 13 assets: five installers, two macOS `.app.tar.gz` tarballs, four `.sig` files, `latest.json` and `SHA256SUMS`, built, smoke-tested, signed and attested by `release.yml`.
- The hub image is on GHCR as `0.4.0`, `0.4` and `latest` with one digest.
- The owner's "Check now" in an installed v0.4.0 answers "up to date" on Windows, macOS and Linux, or the platform that does not is named.
- `main` and `dev` keep their common history (merge commits only); `rust (windows)` is required on `main`.
- Every claim in README, `Docs/hub.md`, CHANGELOG, roadmap and checklist is true once the release exists; whatever stayed unverified is named as such.

## Non-goals

- No feature or fix work. A finding goes to the backlog unless it is a blocker (stop rule).
- No change to `release.yml` or `tools/`, no code signing by OS vendors, no performance re-measure. One exception (owner, 2026-11-27): the two hub deploy checks in `tools/test-release-scripts.sh` had the image tag `0.3.1` written into them, so any version bump failed them; they now accept any `X.Y.Z` tag that both deploy files share.
- The deferred owner checks (D, F, G, H) stay deferred. The first real update runs with the release after v0.4.0.

## Anti-goals

- A release with a red check, a new unallowed CodeQL alert, an unfixed High or Medium finding, or a mismatch between tag, `Cargo.toml`, `Cargo.lock`, `package.json` and the two hub deploy files.
- A tag on the wrong commit: the `v*` ruleset forbids moving or deleting it.
- Publishing the draft by hand, deleting a tag or release to repair a run, or reusing the version number of a rejected release.
- Calling signing, publishing, the provenance of `latest.json` or the update check verified before each ran against the real release.
- Any value of the signing key or its password in chat, a file, a log or a command.

## Constraints

- `CLAUDE.md` "Git & branches" and "Releases": branch `release/v0.4.0` from `dev` (`dbde162`); the PR to `main` and the back-merge use "Create a merge commit"; no force push, no `--no-verify`, no branch deletion.
- The plan stops twice: **Stop A** before the PR to `main` and **Stop B** before the tag push. The go at Stop B also covers the back-merge. The branch protection change on `main` needs its own word.
- The job `sign` runs in the Environment `release-signing`, which has a required reviewer: the owner approves the deployment in GitHub during the run. Claude does not approve it.
- Native cargo is blocked on the development machine: cargo commands run in the Linux container `fernjo-dev`; Windows-only code is covered by CI (`rust (windows)`). No WebView2 runtime: installers come from CI only.
- Release notes on GitHub are short, hand-written and user-readable.
- `main` requires `roadmap`, `rust`, `ui`, `tauri-build`, `cargo-deny`, `workflows` and an up-to-date branch.

## Approaches

1. **`CLAUDE.md` "Releases" sequence (chosen):** release branch, bump and docs, gate, PR to `main`, tag on `origin/main`, draft, `release.yml` signs and publishes, post-release checks, back-merge, evidence PR.
2. Squash into `main` or release from `dev`: rejected, both break `CLAUDE.md`.
3. A signed trial tag first: rejected, a `v*` tag cannot be deleted and the release would be permanent. The local rehearsal with the test key and the key copy check (M14) stand in for it.
4. Run the deferred owner checks first: not chosen; the owner deferred them on 2026-11-27.

## Design

1. Release edits on `release/v0.4.0`: versions `0.4.0` (`Cargo.toml`, refreshed `Cargo.lock`, `package.json`), hub image tag in `compose.yaml` and `fernjo-hub.container`, `CHANGELOG.md` `[Unreleased]` becomes `[0.4.0] - <release date>` naming M13 and M14, README (status line; the "Install" section names every asset of a release from v0.4.0 on), the image tag in the commands of `Docs/hub.md` (the dated evidence for 0.3.1 stays), roadmap release `0.4.0` done with its date.
2. Gate on that tree and a delta check since the M14 evidence (`c140113`; only documents expected); a section "v0.4.0 result" in `Docs/release-checklist.md` with the known gaps carried over.
3. **Stop A**, then the PR to `main`; all checks and the `release.yml` dry run green; merge with a merge commit.
4. **Stop B**, then tag `origin/main`, push, create the draft at once. The owner approves `release-signing`. Watch the run.
5. Verify the release: asset list, `sha256sum -c`, `verify-installers.sh --release`, `write-latest-json.mjs --check`, the four signatures against the shipped public key, `gh attestation verify` per installer and for `latest.json`, the feed URL the app uses, the hub image. The owner runs check C.
6. Back-merge PR; require `rust (windows)` on `main`; evidence PR to `dev` (checklist result, roadmap acceptance, `CLAUDE.md` statements that said "never run").

## Stop rule

Stop and report, without a workaround, when: a gate command or CI check is red; CodeQL reports an alert the owner has not allowed to dismiss; the delta holds unreviewed code with a High or Medium issue; `git status` or a diff shows something unexpected; the tag would point anywhere but the merge commit of the release PR; the release run fails or the assets, signatures or attestations are wrong. A failed run is repeated with `gh run rerun <run id> --failed` while the release is a draft. A failure that needs a change to the workflow or the code cannot be fixed under this tag: the fix is released as v0.4.1, and what happens to the draft is the owner's decision. A platform that fails check C cannot update itself and needs v0.4.1 before users rely on it.

## Left to the builder

Wording of README, release notes, CHANGELOG and checklist text; dispositions of new Low findings; how the evidence PR is cut.
