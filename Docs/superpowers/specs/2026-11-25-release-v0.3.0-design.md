# Release v0.3.0: design

Date: 2026-11-25 · Status: approved in chat by the owner ("okay", 2026-11-25); the irreversible steps still need their own go (see Constraints)

## Intent

Publish v0.3.0, "Sync, daily-use features and security check" (milestones 9, 10 and 11): multi-device sync through the self-hosted `fernjo-hub`, quick connect, reopened tabs, vault auto-lock, Pageant, native paste, and the hardening of M11. It repeats the sequence of v0.1.1 and v0.2.0 (`2026-11-21-release-v0.2.0-design.md`) with the tag-then-draft flow that `release.yml` has had since PR #50: the tag push starts the build, the draft release receives the installers and the workflow publishes it (releases are immutable).

## Goals

- `v0.3.0` is a published GitHub release on `main` with five installers and `SHA256SUMS`, built, smoke-tested and attested by `release.yml`.
- `main` and `dev` keep their common history (merge commits only).
- Every claim in README, CHANGELOG, roadmap and checklist is true once the release exists; whatever stayed unverified is named as such.

## Non-goals

- No feature or fix work. A finding goes to the backlog unless it is a blocker (stop rule).
- No change to `release.yml`, no code signing, no performance re-measure (not possible here: no WebView2 runtime; the CHANGELOG and checklist say so).
- Dependabot PR #49 was handled before this branch (merged into `dev` as `8bd25a0`, on the owner's explicit instruction for that PR only); future Dependabot PRs remain the owner's.

## Anti-goals

- A release with a red check, a CodeQL alert that is new to `main` and not allowed by the owner, an unfixed High or Medium finding, or a mismatch between tag, `Cargo.toml`, `Cargo.lock` and `package.json`.
- A tag on the wrong commit: the `v*` ruleset forbids moving or deleting it.
- Publishing the draft by hand, or repairing a half-published state by deleting tags or releases.
- Describing the provenance attestation as verified before `gh attestation verify` has run against the real one.

## Constraints

- `CLAUDE.md` "Git & branches" and "Releases": branch `release/v0.3.0` from `dev`; PR to `main` and the back-merge use "Create a merge commit"; no force push, no `--no-verify`, no branch deletion. A merge to `main` and the release happen only on the owner's explicit instruction. The plan therefore stops twice: **Stop A** before the PR to `main` (evidence report, go for merge) and **Stop B** right before the tag push (it cannot be undone). The go at Stop B also covers the back-merge.
- `tools/check-release-version.sh` accepts only `[v]MAJOR.MINOR.PATCH`; `Cargo.toml`, `package.json` and the tag must agree or the release build fails.
- `main` requires `roadmap`, `rust`, `ui`, `tauri-build`, `cargo-deny`, `workflows` and an up-to-date branch.
- No WebView2 runtime on this machine: installers exist only through the CI dry run and the release run.
- CodeQL alerts are dismissed only on the owner's explicit word.

## Approaches

1. **`CLAUDE.md` "Releases" sequence (chosen):** release branch, bump and docs, gate, PR to `main` (merge commit), tag on `origin/main`, draft, `release.yml` publishes, back-merge, evidence PR.
2. Squash into `main`: rejected (`CLAUDE.md`).
3. Release from `dev`: rejected, `main` holds only published states.
4. Wait for the Linux checks, the performance run and the `fernjo-fs` macOS test job first: not chosen; the owner closed M11 knowing they were open, and they are recorded as known gaps ("Known gaps" in the "v0.3.0 readiness" section).

## Design

1. Preconditions: `dev` at `8bd25a0` has green CI and CodeQL, no open PR, no open code-scanning alert; the only open Dependabot alert is `glib` (accepted since M0).
2. Release edits on `release/v0.3.0`: versions `0.3.0` (`Cargo.toml`, refreshed `Cargo.lock`, `package.json`), `CHANGELOG.md` `[Unreleased]` becomes `[0.3.0] - 2026-11-25` naming M9, M10 and M11, README status line, roadmap release `0.3.0` done with its date.
3. Gate on that tree and a delta check since the "v0.3.0 security review" (only #49, #50, #51 and #52 came after it): the checklist commands, `gh api` code-scanning alerts, `pnpm audit --prod`, gitleaks over the history; a section "v0.3.0 result" in `Docs/release-checklist.md` with the known-gaps table carried over from "v0.3.0 readiness".
4. **Stop A**, then PR to `main`; all checks and the `release.yml` dry run green (including "Check the binary for build paths"), merge with a merge commit.
5. **Stop B**, then `git tag v0.3.0 origin/main`, push the tag, create the draft at once; watch the run; `publish` publishes. Verify: release not a draft, five installers and `SHA256SUMS`, `sha256sum -c`, `tools/verify-installers.sh`, and `gh attestation verify` on one installer.
6. Back-merge PR `main` into `dev` (merge commit); evidence PR to `dev` (checklist result, CLAUDE.md sentence on provenance, roadmap block, DECISIONS if the flow needed a fix).

## Stop rule

Stop and report, without a workaround, when: a gate command or CI check is red; CodeQL reports an alert the owner has not allowed to dismiss; the review delta shows a High or Medium issue; `git status` or a diff shows something unexpected; the tag would point anywhere but the merge commit of the release PR; the release run fails or the attached files or the attestation are wrong. A failed run is repeated with `gh run rerun <run id> --failed` while the release is still a draft; deleting a tag or release is the owner's decision.

## Left to the builder

Wording of README, CHANGELOG and checklist text; dispositions of new Low findings (accept with a reason, or backlog); whether the evidence PR can be folded into fewer edits once everything is known.
