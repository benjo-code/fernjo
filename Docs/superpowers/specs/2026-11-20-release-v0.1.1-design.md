# Release v0.1.1: design

Date: 2026-11-20 · Status: awaiting the owner's approval in chat

## Intent

Publish v0.1.1, "Polish and hardening" (milestone 7): no silent loss of synced `connections.json` data, quit confirmation, tabs that close on a deliberate shell exit, resizable panels, multi-select in the tree, a UI whose vault, import and settings can be found without a hint, and the Low findings of the M6 reviews settled. It repeats the sequence of the v0.1.0 release (`2026-11-18-release-v0.1.0-design.md`), so the owner can use the fixed installers and the data-safety fixes.

## Goals

- `v0.1.1` exists as a GitHub release on `main` with five installers and `SHA256SUMS`, built and smoke-tested by `release.yml`.
- `main` and `dev` keep their common history (merge commits only).
- Every claim in README, CHANGELOG, the roadmap and the checklist is true once the release exists; anything unverified is named as such.

## Non-goals

- No new features or fixes. Anything found during the release goes to the backlog, unless it is a blocker (then the stop rule applies).
- No code signing, no auto-update, no change to `release.yml`.
- The owner-machine manual checks of M7 (waived by the owner on 2026-11-20) are not run; they are listed as accepted known gaps.

## Anti-goals

- A release that goes out with a red check, a new unreviewed CodeQL alert, an unfixed High or Medium security finding, or a version mismatch between tag, `Cargo.toml` and `package.json`.
- A half-published state repaired by deleting and recreating releases or tags without the owner's decision.
- Describing a waived or unverified check as verified.

## Constraints

- `CLAUDE.md` "Git & branches" and "Releases": branch `release/vX.Y.Z` from `dev`; PRs to `main` and the back-merge to `dev` use "Create a merge commit"; no force push, no `--no-verify`, no deleting branches.
- `tools/check-release-version.sh` accepts only `[v]MAJOR.MINOR.PATCH`.
- `main` requires the checks `roadmap`, `rust`, `ui`, `tauri-build`, `cargo-deny`, `workflows` and an up-to-date branch.
- The reusable checklist (`Docs/release-checklist.md`) wants its steps run on the exact commit the release is cut from. `dev` is at `6cd1672` (the M7 merge); its push CI run was still in progress when this was written and must be green first.
- CodeQL alerts are dismissed only on the owner's explicit instruction.

## Approaches

1. **Checklist step 9 sequence, as for v0.1.0 (chosen):** `release/v0.1.1` from `dev`, bump and docs, gate, PR to `main` (merge commit), `gh release create v0.1.1 --target main`, back-merge `main` into `dev`.
2. Squash-merge into `main`: rejected, `CLAUDE.md` forbids it (histories diverge).
3. Release from `dev` directly: rejected, `main` holds only published states.
4. A pre-release tag as a rehearsal: rejected, the version script refuses it, and the attach step was rehearsed already (run `44378870114`).

## Design

Owner decision (2026-11-20): the plan covers the whole sequence including the irreversible steps (merge to `main`, creating the release, back-merge); the owner's go is given in advance, **unless something goes wrong** (stop rule below).

1. **Preconditions.** The push CI runs (`CI`, `CodeQL`) of `dev` at `6cd1672` are green, and the working tree is clean.
2. **Release branch.** `release/v0.1.1` from `dev`. Bump `[workspace.package] version` in `Cargo.toml` (commit the refreshed `Cargo.lock`) and `package.json` to `0.1.1`. `CHANGELOG.md`: `[Unreleased]` becomes `[0.1.1] - 2026-11-20` naming milestone M7, with a new empty `[Unreleased]` above it. README: check its claims against M7 (features, shortcut table against `ui/src/lib/shortcuts.ts`, the status line that names v0.1.0 as the published release) and change only what is no longer true. `Docs/roadmap.json`: release `0.1.1` done with its date, then `dotnet run tools/roadmap.cs -- generate`.
3. **Checklist on that commit.** Run the reusable checklist for the delta since v0.1.0 and write a section "v0.1.1 result" in `Docs/release-checklist.md`:
   - gate commands: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm lint`, `cargo deny check`, `bash tools/check-workflows.sh`, `bash tools/test-release-scripts.sh`, `bash tools/check-release-version.sh v0.1.1`, `dotnet run tools/roadmap.cs -- check`;
   - security review of the `v0.1.0..dev` diff: `/security-review`, `gh api repos/benjo-code/fernjo/code-scanning/alerts?state=open` empty, gitleaks over the history, and the delta items of the v0.1.0 review that M7 touched (vault KDF cap, atomic writes, import limits, webview arguments, release-binary hygiene);
   - the known-gaps table with a disposition per entry (the waived owner checks, the unproven Linux icon attempt, the Apple Silicon dmg and `.deb` on real hardware, anything new) and a verdict line per area plus an overall line;
   - the build-path check (checklist step 8) of the release PR's dry run, with its run URL.
   A verdict other than "no blocker" stops the release.
4. **PR to `main`.** All checks green (the required ones, the `release.yml` dry run with five installers and smoke tests, CodeQL), then merge with a merge commit.
5. **Release.** `gh release create v0.1.1 --target main --title "v0.1.1" --notes-file <CHANGELOG section>`. Watch `release.yml`; check that the release holds the five installers and `SHA256SUMS`, that `sha256sum -c SHA256SUMS` passes on the downloaded files and that `tools/verify-installers.sh 0.1.1 <dir>` exits 0.
6. **Back-merge.** PR `main` into `dev`, merge commit.
7. **Evidence.** A small docs PR to `dev` (squash allowed) adds PR numbers, the merge commit, the run ids and the asset check to the "v0.1.1 result" section.

## Stop rule

Stop and report, without trying a workaround, when: a gate command or a CI check is red; CodeQL reports a new alert; the security review finds a High or Medium issue that is not already fixed; `git status` or a diff contains something unexpected; the release workflow fails or the attached files are wrong. No deleting or re-creating of the release or the tag without the owner's decision.

## Left to the builder

Exact wording of the README and CHANGELOG edits, the evidence text in the roadmap and checklist, the dispositions of any new low findings (accept with a reason or backlog), and whether the evidence PR is needed once everything is recorded before the release.
