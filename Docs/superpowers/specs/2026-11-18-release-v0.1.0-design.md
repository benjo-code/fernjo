# Release v0.1.0: design

Date: 2026-11-18 · Status: approved by the owner in chat on 2026-11-18

## Intent

Publish the first release of fernjo: connection tree, vault, SSH tabs and mRemoteNG import with installers for Windows, macOS and Linux (the "Daily SSH driver", M0 to M6). `Docs/release-checklist.md` ends with "ready for the owner to decide, no blocker left"; this design turns that decision into an executed release.

## Goals

- `v0.1.0` exists as a GitHub release on `main` with five installers and `SHA256SUMS`, built and smoke-tested by `release.yml`.
- `main` and `dev` keep their common history (merge commits only).
- Every claim in README, CHANGELOG and the roadmap is true once the release exists.

## Non-goals

- No new features or fixes. Post-v0.1.0 items stay in the backlog.
- No code signing, no auto-update, no change to `release.yml`.
- No re-verification of the owner-reported manual checks (the checklist states them as reports).

## Anti-goals

- A release that goes out with a red check, a new unreviewed CodeQL alert or a version mismatch between tag, `Cargo.toml` and `package.json`.
- A half-published state that is repaired by deleting and recreating releases or tags without the owner's decision.

## Constraints

- `CLAUDE.md` "Git & branches" and "Releases": branch `release/vX.Y.Z` from `dev`; PR to `main` and the back-merge PR use "Create a merge commit"; no force push, no `--no-verify`, no deleting branches.
- `tools/check-release-version.sh` accepts only `[v]MAJOR.MINOR.PATCH`.
- The checklist requires the gate on the exact commit the release is cut from; the last full evidence is at `408d66b`, `dev` is at `977dab4` (docs only since).
- CodeQL alerts are dismissed only on the owner's explicit instruction.

## Approaches

1. **Checklist step 8 sequence (chosen):** `release/v0.1.0` from `dev`, bump and docs, gate, PR to `main` (merge commit), `gh release create v0.1.0 --target main`, back-merge `main` into `dev`.
2. Squash-merge into `main`: rejected, `CLAUDE.md` forbids it (history of `main` and `dev` diverges).
3. Release from `dev` directly: rejected, `main` holds only published states.
4. A pre-release tag (`-rc`) as a rehearsal: rejected, the version script refuses it and the attach step was already rehearsed with `v0.0.0` (run `44378870114`).

## Design

Owner decision (2026-11-18): the plan covers the whole sequence including the irreversible steps; the owner's go for steps 3 to 5 is given in advance, **unless something goes wrong**.

1. **Release branch.** `release/v0.1.0` from the current `dev`. Bump `[workspace.package] version` in `Cargo.toml` (a build refreshes `Cargo.lock`, commit it) and `package.json` to `0.1.0`. `CHANGELOG.md`: `[Unreleased]` becomes `[0.1.0] - 2026-11-18` naming M0 to M6, with a new empty `[Unreleased]` above it. README: the "not published yet" statements become true for the published release. `Docs/roadmap.json`: release v0.1.0 done with date and evidence, then `dotnet run tools/roadmap.cs -- generate`. `Docs/release-checklist.md`: a short result section for the release commit.
2. **Gate on that commit.** `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, `pnpm test`, `pnpm lint`, `cargo deny check`, `bash tools/check-workflows.sh`, `bash tools/test-release-scripts.sh`, `bash tools/check-release-version.sh v0.1.0`, `dotnet run tools/roadmap.cs -- check`.
3. **PR to `main`.** All checks green (CI, roadmap, the `release.yml` dry run with five installers and smoke tests, CodeQL), then merge with a merge commit.
4. **Release.** `gh release create v0.1.0 --target main --title "v0.1.0" --notes "<CHANGELOG section>"`. Watch the `release.yml` run; check that the release holds the five installers and `SHA256SUMS` and that `sha256sum -c SHA256SUMS` passes on the downloaded files.
5. **Back-merge.** PR `main` into `dev`, merge commit.

## Stop rule

Stop and report, without trying a workaround, when: a gate command or a CI check is red; CodeQL reports a new alert; the diff or `git status` contains something unexpected; the release workflow fails or the attached files are wrong. No deleting or re-creating of the release or the tag without the owner's decision.

## Left to the builder

Exact wording of the README and CHANGELOG edits, the evidence text in the roadmap and checklist, and how the evidence of the release run is recorded after the fact (a small docs PR to `dev` after the back-merge, if needed).
