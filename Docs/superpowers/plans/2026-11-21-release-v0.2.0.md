# Release v0.2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish fernjo v0.2.0 ("RDP", milestone 8) as a GitHub release on `main` with five installers and `SHA256SUMS`, and bring `dev` back in line with `main`.

**Architecture:** The sequence of step 9 in `Docs/release-checklist.md`, as for v0.1.1: a `release/v0.2.0` branch carries the version bump, the docs and the checklist result; a merge-commit PR moves it to `main`; `gh release create` triggers `release.yml` (build, smoke test, publish); a merge-commit PR brings `main` back into `dev`; a small docs PR records the evidence. Unlike v0.1.1 the owner has not pre-authorised the irreversible steps: Tasks 1 to 3 prepare and push the branch, Task 4 opens the PR, and **Tasks 5 to 7 (merge to `main`, release, back-merge) wait for the owner's go**.

**Tech Stack:** git, `gh`, bash, Docker (gitleaks), the repo's gate commands (cargo, pnpm, dotnet for `tools/roadmap.cs`), GitHub Actions (`release.yml`).

**Spec:** `Docs/superpowers/specs/2026-11-21-release-v0.2.0-design.md` (awaiting the owner's approval in chat)

## Global Constraints

- Branch `release/v0.2.0` from `dev` (exists, created from `dev` at `09d08b7`); never commit to `dev` or `main` directly.
- PR `release/v0.2.0` → `main` and PR `main` → `dev` are merged with **"Create a merge commit"** (`gh pr merge <n> --merge`), never squash or rebase.
- No force push, no `--no-verify`, no deleting branches, tags or releases without the owner's decision. `spike/m08-rdp-canvas` and Dependabot PR #3 stay untouched.
- `tools/check-release-version.sh` accepts only `[v]MAJOR.MINOR.PATCH`; tag `v0.2.0`, `[workspace.package] version` in `Cargo.toml` and `version` in `package.json` must all be `0.2.0`.
- Commits follow Conventional Commits, **no attribution lines** in commit messages or PR bodies; stage files selectively (`git add <file>`, never `-A`); after every commit check `git show --stat HEAD` against the expected files.
- CodeQL alerts are dismissed only on the owner's explicit instruction.
- "Done" means each command's result is stated; anything not run is marked open and never described as verified. A run from `pnpm tauri dev` is never described as a run of the installer.
- Stop rule: stop and report, with no workaround, when a gate command or CI check is red, CodeQL reports an alert other than #122 to #127 (or one the owner has not allowed to dismiss), the security review finds a High or Medium issue that is not already fixed, `git status` or a diff shows something unexpected, the release workflow fails or the attached files are wrong.
- This machine has no WebView2 runtime files: `pnpm tauri build` and the app do not run here. Installers come only from CI.

## Review Focus

- Alerts #122 to #127 (`rust/hard-coded-cryptographic-value`, made-up sentinel passwords in RDP test code) exist on `dev` but not on `main`; the release PR's `CodeQL` result check will report them as new and block the merge. They need the owner's word to be dismissed as "used in tests" (as 106 to 118 were before v0.1.0); without it Task 4 stops.
- RDP has only run from `pnpm tauri dev` on the owner's machines. A release build embeds `ui/dist` and applies the CSP (`default-src 'self'; connect-src ipc: http://ipc.localhost; style-src 'self' 'unsafe-inline'; img-src 'self' data:`); the dry-run installers prove start-up only, not an RDP session. The optional installer check (Task 4 Step 4) is the only way to see it; the CHANGELOG and README must say what was and was not run.
- The README privacy paragraph says "fernjo's own code makes no network connections except the SSH sessions you open"; with RDP that is false and must change before the release, not after.
- `Cargo.lock` holds six workspace crates (now including `fernjo-rdp`); a stale lock after the bump fails every `--locked` job. Its diff may contain only version lines of workspace crates.
- `deny.toml` ignores `RUSTSEC-2023-0071` because IronRDP's `picky` pins `rsa =0.10.0-rc.18`, so SSH RSA-key signing in the shipped app runs on a release candidate (owner decision 2026-11-20). The release notes and the checklist verdict must state this, not hide it, and `cargo deny check` must still pass with exactly the documented ignores (the Linux-only unmatched entries warn on Windows).
- A hostile RDP server controls bitmap sizes, clipboard data and the certificate; the review must look at the caps in `fernjo-rdp` (`framebuffer.rs`, `text_clipboard.rs`) and at the certificate decision order in `connect.rs` (prompts only after the certificate was accepted), and the three RDP commands must be in `no_response_contains_a_secret`.
- Between the release event and the end of `publish` the public release has no assets; an empty release after the run is the failure.
