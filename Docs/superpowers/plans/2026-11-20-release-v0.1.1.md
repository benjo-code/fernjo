# Release v0.1.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish fernjo v0.1.1 ("Polish and hardening", milestone 7) as a GitHub release on `main` with five installers and `SHA256SUMS`, and bring `dev` back in line with `main`.

**Architecture:** The sequence of step 9 in `Docs/release-checklist.md`, as for v0.1.0: a `release/v0.1.1` branch carries the version bump, the docs and the checklist result; a merge-commit PR moves it to `main`; `gh release create` triggers `release.yml` (build, smoke test, publish); a merge-commit PR brings `main` back into `dev`; a small docs PR records the evidence.

**Tech Stack:** git, `gh`, bash, Docker (gitleaks), the repo's gate commands (cargo, pnpm, dotnet for `tools/roadmap.cs`), GitHub Actions (`release.yml`).

**Spec:** `Docs/superpowers/specs/2026-11-20-release-v0.1.1-design.md` (approved by the owner in chat on 2026-11-20, including the advance go for the irreversible steps)

## Global Constraints

- Branch `release/v0.1.1` from `dev`; never commit to `dev` or `main` directly.
- PR `release/v0.1.1` → `main` and PR `main` → `dev` are merged with **"Create a merge commit"** (`gh pr merge <n> --merge`), never squash or rebase.
- No force push, no `--no-verify`, no deleting branches, tags or releases without the owner's decision.
- `tools/check-release-version.sh` accepts only `[v]MAJOR.MINOR.PATCH`; tag `v0.1.1`, `[workspace.package] version` in `Cargo.toml` and `version` in `package.json` must all be `0.1.1`.
- Commits follow Conventional Commits, **no attribution lines** in commit messages or PR bodies; stage files selectively (`git add <file>`, never `-A`); after every commit check `git show --stat HEAD` against the expected files.
- CodeQL alerts are dismissed only on the owner's explicit instruction.
- "Done" means each command's result is stated; anything not run is marked open and never described as verified. The M7 owner-machine checks are waived by the owner (2026-11-20) and appear only as accepted known gaps.
- Stop rule (owner decision 2026-11-20: all steps are pre-authorised **unless something goes wrong**): stop and report, with no workaround, when a gate command or CI check is red, CodeQL reports a new alert, the security review finds a High or Medium issue that is not already fixed, `git status` or a diff shows something unexpected, the release workflow fails or the attached files are wrong.

## Review Focus

- A stale `Cargo.lock` after the bump makes every `--locked` command and CI job fail: the refreshed lock goes into the same commit as the version, and its diff may contain only version lines of workspace crates.
- `main` requires `roadmap`, `rust`, `ui`, `tauri-build`, `cargo-deny`, `workflows` and an up-to-date branch (`strict`); a PR that is behind `main` cannot merge.
- Between the release event and the end of `release.yml`'s `publish` job the public release has no assets; an empty release after the run is the failure.
- `check-release-version.sh` runs inside the release run against the tag's commit, so it runs locally first.
- The CHANGELOG `[Unreleased]` text makes claims that must still be true at release time: "proven only by the first release build" (build paths) and "unconfirmed until looked at" (Linux icon). The first is settled or not by the dry run of PR #16; the second stays unconfirmed. Wording follows the evidence.
- The README and roadmap say "released" before the release exists (they ship in the release PR); if the release fails, fix that state before anything else.
- The back-merge PR can conflict only if someone pushed to `dev` meanwhile; then stop and report.
