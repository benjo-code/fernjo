# Release v0.4.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish fernjo v0.4.0 ("Automatic updates", milestones 13 and 14) as a GitHub release on `main` with signed update files, and bring `dev` back in line with `main`.

**Architecture:** `CLAUDE.md` "Releases" and step 9 of `Docs/release-checklist.md`: a `release/v0.4.0` branch carries the version bump, docs and gate result; a merge-commit PR moves it to `main`; the pushed tag `v0.4.0` starts `release.yml`, which builds, signs (after the owner's approval), verifies, attests, attaches to the draft and publishes; the published release is checked, `main` is merged back and the evidence recorded.

**Tech Stack:** git, `gh`, Git Bash and `pnpm`/`node`/`dotnet` on Windows, Docker (`fernjo-dev` for cargo, gitleaks, buildx), GitHub Actions.

**Spec:** `Docs/superpowers/specs/2026-11-27-release-v0.4.0-design.md`

## Global Constraints

- Branch `release/v0.4.0` (exists locally, from `dev` = `dbde162`, not pushed). Never commit to `dev` or `main` directly.
- PR `release/v0.4.0` → `main` and PR `main` → `dev` are merged with **"Create a merge commit"** (`gh pr merge <n> --merge`). The evidence PR may be squashed.
- No force push, no `--no-verify`, no deleting branches, tags or releases. Never merge a Dependabot PR.
- Conventional Commits, **no attribution lines** in commits or PR bodies; `git add <file>` only; `git show --stat HEAD` after every commit.
- No change to `release.yml`, `tools/` or application code. A finding goes to the backlog unless it is a blocker. One exception (owner, 2026-11-27, found in Task 3 Step 2): the hub deploy checks in `tools/test-release-scripts.sh` no longer name a version, in a commit of their own.
- Three owner moments are not Claude's to take: **Stop A** (before the PR to `main`), **Stop B** (before the tag push; covers the back-merge), the approval of the `release-signing` deployment in GitHub. Changing branch protection on `main` needs its own word.
- Never ask for, print or handle the signing key or its password. CodeQL alerts are dismissed only on the owner's word.
- Never publish the draft by hand; never move or delete a `v*` tag; never reuse the version number of a rejected release.
- Say what was not run. The signing, publish and update-check claims are "unverified" until they ran against the real release.
- **Stop rule:** stop and report, with no workaround, when a gate command or CI check is red, CodeQL reports an alert not allowed to dismiss, the delta holds unreviewed code with a High or Medium issue, `git status` or a diff shows something unexpected, the tag would point anywhere but the merge commit of the release PR, or the release run, its assets, signatures or attestations are wrong.
- `<scratchpad>` is the session's scratchpad directory; every download goes into a new, empty folder below it.
- Native cargo is blocked on this machine. `fc "<cargo command>"` below means:

```bash
fc() { MSYS_NO_PATHCONV=1 docker run --rm -v "d:/VS-Code/fernjo:/src" -v fernjo-target:/target -v fernjo-cargo:/opt/cargo/registry -v fernjo-rustup:/opt/rustup ${FC_EXTRA:-} fernjo-dev bash -c "cd /src && export CARGO_TARGET_DIR=/target CARGO_HOME=/opt/cargo && $1"; }
```

## Review Focus

- **A blind replace of `0.3.1`.** `Cargo.toml` pins `ironrdp-core = "=0.3.1"`; CHANGELOG, DECISIONS, `Docs/hub.md` evidence and `tools/test-release-scripts.sh` fixtures name 0.3.1 on purpose. Pinned in Task 2 Step 6.
- **A CHANGELOG section `latest.json` cannot be written from.** `publish` would fail after signing, and a fix on `main` needs a new tag. Pinned in Task 2 Step 3 and Task 5 Step 1.
- **Wrong signing secrets.** `sign` can succeed with the wrong key and only `verify-signatures` fails; "Re-run failed jobs" then does not sign again. Handled in Task 5 Step 6.
- **A published release the app cannot update from:** not marked latest, or the feed URL does not serve the signed `latest.json`. Immutable, so it needs v0.4.1. Pinned in Task 6 Steps 1 and 3.
- **The hub image moves before the release exists.** `hub-image` pushes `latest` before `publish`; if the release then fails for good, `latest` points at an unreleased version. Tell the owner in that case (Task 5 Step 6).
