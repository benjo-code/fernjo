# Release v0.3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish fernjo v0.3.0 ("Sync, daily-use features and security check", milestones 9, 10 and 11) as a GitHub release on `main` with five installers and `SHA256SUMS`, and bring `dev` back in line with `main`.

**Architecture:** The sequence of step 9 in `Docs/release-checklist.md` and `CLAUDE.md` "Releases", in the tag-then-draft form of `release.yml` (PR #50): a `release/v0.3.0` branch carries the version bump, the docs and the checklist result; a merge-commit PR moves it to `main`; a pushed tag `v0.3.0` starts `release.yml`, a draft release made right after receives the attested installers and the workflow publishes it; a merge-commit PR brings `main` back into `dev`; a small docs PR records the evidence. The owner has not pre-authorised the irreversible steps: Tasks 1 to 3 prepare and push the branch, Stop A (Task 4) asks before the PR to `main` is opened and merged, Stop B (Task 5) asks before the tag is pushed.

**Tech Stack:** git, `gh`, bash (Git Bash on Windows), Docker (gitleaks), the repo's gate commands (cargo, pnpm, dotnet for `tools/roadmap.cs`), GitHub Actions (`release.yml`).

**Spec:** `Docs/superpowers/specs/2026-11-25-release-v0.3.0-design.md` (approved in chat on 2026-11-25)

## Global Constraints

- Branch `release/v0.3.0` from `dev` (exists locally, created at `dev` = `8bd25a0`, not yet pushed); never commit to `dev` or `main` directly.
- PR `release/v0.3.0` → `main` and PR `main` → `dev` are merged with **"Create a merge commit"** (`gh pr merge <n> --merge`), never squash or rebase. Feature and docs PRs to `dev` may be squashed.
- No force push, no `--no-verify`, no deleting branches, tags or releases without the owner's decision. Dependabot PRs are the owner's (the exception for #49 is spent).
- `tools/check-release-version.sh` accepts only `[v]MAJOR.MINOR.PATCH`; tag `v0.3.0`, `[workspace.package] version` in `Cargo.toml` and `version` in `package.json` must all be `0.3.0`.
- Commits follow Conventional Commits, **no attribution lines** in commit messages or PR bodies; stage files selectively (`git add <file>`, never `-A`); after every commit check `git show --stat HEAD` against the expected files.
- CodeQL alerts are dismissed only on the owner's explicit word.
- "Done" means each command's result is stated; anything not run is marked open and never called verified. A run from `pnpm tauri dev` is never described as a run of the installer.
- Never publish the draft release by hand (a published release takes no installers); never move or delete a `v*` tag.
- Stop rule: stop and report, with no workaround, when a gate command or CI check is red, CodeQL reports an alert the owner has not allowed to dismiss, the delta review finds a High or Medium issue, `git status` or a diff shows something unexpected, the tag would point anywhere but the merge commit of the release PR, or the release run fails or the attached files or the attestation are wrong.
- This machine has no WebView2 runtime files: `pnpm tauri build` and the app do not run here. Installers come only from CI.
- Scratch files go in `C:\Users\benja\AppData\Local\Temp\claude\8f152d1aa137d747\0eca399c-400f-46e8-9253-ca65271bc44d\scratchpad` (called `<scratchpad>` below), downloads into a new, empty folder each.

## Review Focus

- **Lock file churn.** `Cargo.lock` holds nine workspace crates (`fernjo-app`, `fernjo-core`, `fernjo-fs`, `fernjo-hub`, `fernjo-import`, `fernjo-rdp`, `fernjo-ssh`, `fernjo-sync`, `fernjo-vault`); after the bump its diff may contain only their `version = "0.2.0"` → `"0.3.0"` lines. A stale lock fails every `--locked` job. `src-tauri/resources/THIRD-PARTY-NOTICES.md` is a committed placeholder: a local run of the notices script overwrites it, and it must not appear in any diff.
- **CodeQL result check on the release PR.** Open alerts on `dev` are 0, but `main` lacks all of M9 to M11, so the PR check may list alerts as new (the M11 PR #48 had 8, all in test code, dismissed by the owner). Any alert needs the owner's word before the merge; without it Task 4 stops.
- **The tag cannot be undone** (`v*` ruleset). Before the push, `origin/main` must hold exactly the release PR's merge commit, with `version = "0.3.0"` in `Cargo.toml` and `package.json` and a `[0.3.0]` heading in `CHANGELOG.md`; the push of the tag is the first run of the draft-then-publish flow and of the provenance attestation, which nobody has seen work.
- **Draft timing.** `publish` refuses a missing or already published release, so the draft must exist before the build jobs finish; create it directly after the tag push. An empty published release or a still-draft release after the run is the failure.
- **Claims that were never verified.** Attestation (`gh attestation verify` not yet run against a real one), `fernjo-fs` on macOS (CI tests Linux only), performance (not re-measured since 0.1.1), the Linux Secret Service and a Linux device in sync. CHANGELOG, README and the checklist verdict must say so and must not claim performance numbers for 0.3.0.
