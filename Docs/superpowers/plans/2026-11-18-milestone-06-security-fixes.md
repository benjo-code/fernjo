# Milestone 6 security fixes (before v0.1.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the three Medium findings of the v0.1.0 security review that the owner decided to fix before the release (vault rollback, keychain item deletion, trust in a synced `known_hosts`) and add the optional webview navigation guard.

**Architecture:** A device-local folder outside the synced data folder holds state the sync cannot forge or roll back (highest vault generation seen, host keys this device confirmed). The vault gets a generation counter inside its authenticated body (no format bump). Auto-unlock never deletes the keychain item. A navigation guard plugin allows only the app origin.

**Tech Stack:** Rust (`fernjo-core`, `fernjo-vault`, `fernjo-ssh`, Tauri 2.12 shell), Svelte 5 + TypeScript, Vitest.

**Spec / sources:** [Docs/superpowers/specs/2026-11-15-fernjo-design.md](../specs/2026-11-15-fernjo-design.md); findings rows 4, 14, 15, 16 in `Docs/release-checklist.md`; decisions in `Docs/DECISIONS.md` (vault, keychain, known_hosts, "Webview hardening from day one"); `CLAUDE.md`. Scope change: recorded in `Docs/roadmap.json` (M6 `scopeChanges`) in Task 6.

**Owner decisions (2026-11-18):** fix all three Mediums and the navigation guard before v0.1.0. Existing `known_hosts` entries are NOT seeded: every host asks once per device. Accepting an older vault rewrites it at once (`.bak` keeps the old file). The generation counter lives in the encrypted body (no format version change). Device-local folder as specified in Task 2.

## Global Constraints

- **Secrets stay in Rust.** No secret in an IPC response, log, `settings.json`, device-local file or webview storage. A new `#[tauri::command]` follows the three-places rule of `CLAUDE.md` (function plus `handlers` wrapper, `table()` entry in `vault_commands.rs`, `generate_handler!` in `lib.rs`; the count guard must stay green).
- **The owner's real `vault.fernjo` must keep opening and must never be rewritten by a build under test.** Tests use temp dirs and `AppState::open` / in-memory stores. Never touch `%APPDATA%\fernjo`, the real keychain or the real device-local folder; manual runs use a scratch `FERNJO_DATA_DIR` only. Files written for the vault stay atomic with `.bak` and Unix modes 0600/0700.
- **Backward compatibility of the vault:** version stays 1; a v1 file without `generation` reads as generation 0 and is not touched until the first normal save. A golden fixture generated by the CURRENT build BEFORE any vault code changes is the proof (Task 4, step 1).
- **UI:** only tokens from `ui/src/styles/tokens.css`, hex-only CSS, none of `oklch()`, `color-mix()`, `light-dark()`, nesting, `@layer`, `:has()`, container queries; English text; no `{@html}`; TypeScript holds view state only.
- Conventional Commits; stage files by name; `git show --stat HEAD` after each commit; no attribution lines; never `--no-verify`; work on `feature/m06-packaging-release-readiness`; no push by implementers (the controller pushes); no GitHub changes.
- "Done" = fmt, clippy `-D warnings`, `cargo test --workspace` (SSH container tests run only in CI: Docker is not available locally), `pnpm lint`, `pnpm test`, `cargo deny check`, `bash tools/test-release-scripts.sh`, `bash tools/check-workflows.sh`, `dotnet run tools/roadmap.cs -- check` green with results shown.

## Review Focus

1. A stored vault of generation 0 (the owner's existing file) or a file from another device with a HIGHER generation must open without any prompt; only a LOWER generation prompts (Task 4).
2. A planted or half-synced vault file must never delete the keychain item or switch auto-unlock off silently (Task 3).
3. A multi-device user must get at most one clear confirmation per host per device; a host key already confirmed on this device must connect silently; a key that differs from the confirmed one must show the previous fingerprint (Task 5).
4. The navigation guard must not block the app itself: initial load, reload, dev server URL (Task 1).
5. An unwritable device-local folder degrades protection, never blocks connecting or unlocking (Tasks 2, 4, 5).

### Task 3: Auto-unlock never deletes the keychain item

**Files:** `crates/fernjo-vault/src/keystore.rs`, `keystore_tests.rs`, `src-tauri/src/state.rs`, `src-tauri/src/vault_commands.rs`, `src-tauri/src/lib.rs` (comment), UI: `ui/src/lib/types.ts`, `ui/src/lib/components/VaultNote.svelte` (+ tests), `Docs/DECISIONS.md` ("Vault: keychain behaviour"), `CLAUDE.md`.

Facts verified by the design review: the item (service `fernjo`, user = vault id) holds only the 32-byte data key, which never changes (also not on a password change); the vault id is random per vault; a replaced vault has another id and never touches the old item; `open_body` maps both an AEAD and a JSON failure to `tampered`; today `try_auto_unlock` deletes the item on `tampered` and `state.rs` ignores the result. So a damaged, half-synced or planted same-id file switches auto-unlock off silently, and deleting is never justified.

**Interfaces:** `try_auto_unlock` never deletes. Replace `AutoUnlock::StaleKeyRemoved` by `AutoUnlock::KeyNotAccepted`; `Unavailable(String)` stays (Task 4 adds `RolledBack { found: u64, seen: u64 }`). `AppState.auto_unlock_issue: Mutex<Option<AutoUnlockIssue>>` (`KeyNotAccepted` → `"key_not_accepted"`, `Unavailable` → `"unavailable"`), set from the startup outcome, cleared by a successful unlock. `VaultStatus` gains `autoUnlockIssue: Option<&'static str>` (camelCase). `autoUnlock` (item present) stays true; a password unlock with the box ticked overwrites the item through `remember_key` (heals a truly wrong item); unticking uses the existing `vault_set_auto_unlock(false)`. UI lock note line: "Automatic unlock did not work this time (the vault file may be incomplete or damaged). Your stored key was kept. Enter the master password."

### Task 4: Vault rollback protection

**Files:** `crates/fernjo-vault/src/vault.rs`, `error.rs`, `lib.rs`, new `generation.rs`, `keystore.rs`, fixture `crates/fernjo-vault/tests/fixtures/v1-no-generation.fernjo`; `src-tauri/src/state.rs`, `vault_commands.rs`, `lib.rs` (new command); UI `types.ts`, `api.ts`, `vault.svelte.ts`, `testing.ts`, `VaultNote.svelte` (+ tests); `Docs/vault-format.md`, `Docs/DECISIONS.md`, `SECURITY.md`, `CLAUDE.md`.

**Design:** `Body` (in `vault.rs`, `#[serde(default)]`, no `deny_unknown_fields`, covered by the AAD of the 150-byte header) gains `generation: u64` (v1 files read as 0; version stays 1; older readers ignore the field). `save()` serialises a borrowed `BodyOut<'a> { generation, entries: &'a [Entry] }` with `generation = max(body.generation, self.floor).saturating_add(1)` on EVERY save including `change_password`; on success set `body.generation`, `floor` and the device mark; on failure memory untouched.

```rust
pub trait GenerationStore: Send + Sync {
    fn get(&self, vault: VaultId) -> Option<u64>;      // None = unknown or unavailable
    fn raise(&self, vault: VaultId, generation: u64);  // best effort, only ever increases
}
pub struct FileGenerationStore { path: PathBuf }   // <device_dir>/vault-marks.json {"schemaVersion":1,"marks":{"<uuid>":N}}
pub struct MemoryGenerationStore;                  // tests and the no-device-dir fallback
```
`FileGenerationStore` reuses the vault's private atomic write helper (made `pub(crate)`), re-reads right before writing, treats an unreadable/corrupt file as empty. `Vault::attach_generation_store(&mut self, Arc<dyn GenerationStore>)` sets `floor = max(floor, store.get(id))` and raises the mark to the current generation if unlocked (signatures of `open`/`create_with` unchanged). `VaultError::RolledBack { found: u64, seen: u64 }`, code `rolled_back`, text "The vault file is older than the version this device last opened (generation {found}, last seen {seen}). Another device or a sync tool may have put an older copy back." A shared `unlock_inner(key_source, accept_older: bool)` behind `unlock`, `unlock_with_key` and the new `unlock_accepting_older(&mut self, password)`; the check runs AFTER `open_body` succeeds (rollback is revealed only to someone with the password/key) and before touching `self.header`/`self.unlocked`: `floor = max(self.floor, store.get(id))`; `body.generation < floor` and not accepted → `RolledBack`, vault stays locked; else `self.floor = max(floor, generation)` and `raise`. Equal generation is accepted. Accepting does not lower the floor (next save writes `floor + 1`) and re-stamps at once with a best-effort `save()` (owner decision; `.bak` then holds the pre-accept file); a failed re-stamp keeps the unlock and the prompt returns next start. Auto-unlock never accepts older: `AutoUnlock::RolledBack { found, seen }` (keychain item kept, `autoUnlockIssue: "rolled_back"`).

Shell: `AppState.generations: Arc<dyn GenerationStore>` (`FileGenerationStore` under `device_dir` when available and writable, else `MemoryGenerationStore`; `build` calls `attach_generation_store` BEFORE `try_auto_unlock`); `vault_unlock` passes `rolled_back` through as a `CommandError`; new command `vault_unlock_older(password, remember)` (three-places rule). UI: on auto-unlock `rolled_back` the lock note says "Automatic unlock did not open this vault: the file is older than the last version this device opened. Enter the master password to review."; a password unlock failing with `rolled_back` shows the error text and an "Open the older vault" button that calls `vaultUnlockOlder(password, remember)` with the password still in the field.

### Task 5: Hosts confirmed on this device

**Files:** `crates/fernjo-ssh/src/params.rs`, `interaction.rs`, `handler.rs`, `session.rs`, `crates/fernjo-ssh/tests/support`; `src-tauri/src/sessions.rs`; UI `types.ts`, new `ui/src/lib/components/HostKeySyncedPrompt.svelte`, `SessionPrompt.svelte`, `TabStrip.svelte` (+ tests); `SECURITY.md`, `Docs/DECISIONS.md`, `CLAUDE.md`.

**Design:** a key found in the synced `known_hosts` is accepted silently only when this device confirmed the same key for that host and port. State: a second OpenSSH-format file `<device_dir>/known_hosts.confirmed` handled by the existing `KnownHosts` type (no new parser; written atomically with private modes). `ConnectParams.confirmed_hosts: Option<PathBuf>` (`None` disables the layer for tests/embedders; the shell sets it from `device_dir`; with no device dir the layer is in-memory for the process lifetime so a host asks once per run). `session.rs` builds a second `KnownHosts` and passes it to `ClientHandler { confirmed: Option<KnownHosts>, .. }`. `interaction.rs`: `HostKeySyncedPrompt { host, port, key_type, fingerprint, previous: Vec<String> }` and trait method `host_key_synced(&self, prompt) -> impl Future<Output = HostKeyDecision> + Send` with a default implementation delegating to `host_key` (existing implementers compile); `TauriInteraction` overrides it. `handler.rs` `decide` (the check stays inside the handshake, before authentication, as today): `Known` and confirmed `Known` → allow; `Known` and confirmed `Unknown`/`Changed{stored}` → synced prompt (`previous = stored`): `TrustAlways` → `confirmed.add` (or `replace` when `Changed`), `TrustOnce` records nothing, `Reject` → `HostKeyRejected`; `Unknown` + `TrustAlways` → `known_hosts.add` plus `confirmed.add`; `Changed` + `Replace` → `known_hosts.replace` plus `confirmed.replace`; a failure writing the confirmed file is ignored (best effort; worst case one more prompt); failing to write `known_hosts` keeps today's rejection. Shell: `sessions.rs` sets `params.confirmed_hosts = device_dir.map(|d| d.join("known_hosts.confirmed"))`; `PromptView::HostKeySynced { host, port, key_type, fingerprint, previous }` (camelCase, no secret); answers reuse `PromptAnswer::HostKey` (the wire contract comment at the top of `sessions.rs` gains the variant). UI wording: "This host key was added by another device or file. This device has not confirmed it. If you did not add this host yourself on one of your devices, cancel." Buttons "Confirm and connect", "Connect once", "Cancel"; when `previous` is non-empty add "This device previously trusted <fingerprints>". No seeding of existing entries (owner decision): every host asks once per device after the upgrade. Known limits (document): a device dir inside a synced tree loses the protection; repointing a connection to a host this device already trusts is out of scope.
