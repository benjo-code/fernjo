# fernjo

Cross-platform (Windows, macOS, Linux) SSH & RDP connection manager in the spirit of mRemoteNG: connection tree in a sidebar, sessions as tabs in one window, encrypted credential vault, mRemoteNG import. Built primarily for the owner's daily use; open source.

- **Stack:** Rust (edition 2024, Cargo workspace) · Tauri 2 · Svelte 5 + TypeScript (Vite, pnpm) · xterm.js · russh (SSH) · IronRDP (RDP)
- **Language:** Docs, commits, code and comments in English · UI texts English
- **Build:** `cargo build --workspace` · app: `pnpm tauri build` (dev: `pnpm tauri dev`)
- **Test:** `cargo test --workspace` · `pnpm test`
- **Format/lint:** `cargo fmt --all --check` · `cargo clippy --workspace --all-targets -- -D warnings` · `pnpm lint` (ESLint, Prettier, `svelte-check`) · `cargo deny check`

## Project-specific

**Architecture** (details in the spec, §4–5)
- `crates/fernjo-core` (model, tree, inheritance, persistence), `crates/fernjo-vault`, `crates/fernjo-ssh`, `crates/fernjo-rdp`, `crates/fernjo-import`, `crates/fernjo-sync` (sync client, envelope, merge, engine), `crates/fernjo-hub` (the sync hub binary), `crates/fernjo-fs` (the hardened atomic writer and capped reader), `src-tauri/` (Tauri shell, commands, session manager), `ui/` (Svelte frontend). Each crate is created in the milestone that needs it, not earlier.
- Protocol, vault, import, sync, hub and fs crates never depend on Tauri; they are testable without the UI. `fernjo-fs` depends only on `std`, `getrandom` and, on Unix, `libc` (the open flags) and may be used by every crate (also by `fernjo-hub`). `fernjo-hub` never depends on `fernjo-sync` (own copy of the header parser; the 64 MiB limit is pinned against it in a test); `fernjo-hub` is only ever a dev-dependency (of `fernjo-sync` for the end-to-end tests and of `src-tauri` for the `sync_commands` tests), never a normal one.
- Frontend ↔ Rust: Tauri commands for requests, Tauri channels for streaming session data.
- Plain `cargo build/clippy/test --workspace` compiles Tauri as a dev build, which does not embed `ui/dist` (`devUrl` is set), so cargo needs no UI build first. Only `pnpm tauri build` embeds `ui/dist`, and it runs `pnpm ui:build` itself via `beforeBuildCommand`.
- UI styling uses only the tokens in `ui/src/styles/tokens.css` and follows `DESIGN.md`. Shipped CSS stays hex-only and free of `oklch()`, `color-mix()`, `light-dark()`, nesting, `@layer`, `:has()` and container queries (WebKitGTK 4.1 / `safari13` target); `ui/src/styles/tokens.test.ts` guards this and the contrast pairs. A new colour token goes into the light block and both dark blocks.
- Webview hardening (M11): the CSP in `src-tauri/tauri.conf.json` also sets `form-action 'none'`, `base-uri 'self'`, `object-src 'none'` and `frame-ancestors 'none'` (every UI `<form>` uses `onsubmit` with `preventDefault`, so a form must never rely on a native submission), the main window sets `generalAutofillEnabled: false`, and every input that can hold or show a secret carries `autocomplete="new-password"` (`PasswordField`) or `"off"` (reveal inputs, private key, pairing code); `src-tauri/tests/tauri_conf.rs` and `ui/src/lib/secret-inputs.test.ts` pin them, so a new secret input needs the attribute. `security.freezePrototype` is deliberately off until it is checked in a real app (owner). `RdpPlan`'s `Debug` redacts user name and domain like `ConnectParams`. Details: `Docs/DECISIONS.md` "M11 fix wave J".
- Vite must not inline assets (`assetsInlineLimit: 0` in `ui/vite.config.ts`): the CSP only allows fonts from `'self'`, so an inlined `data:` font would be blocked.
- On Windows, stopping a background `pnpm tauri dev` can leave the Vite server (port 1420) and `fernjo.exe` running; the next `pnpm tauri dev` then fails with "Port 1420 is already in use". Check with `Get-NetTCPConnection -LocalPort 1420 -State Listen` and `Get-Process fernjo`, and stop the leftovers.
- Data folder: `<OS config dir>/fernjo/` (`%APPDATA%\fernjo` on Windows) holds `connections.json` (+ `.bak`); the environment variable `FERNJO_DATA_DIR` overrides it. Use it for any manual run that must not touch the real data. The device-local folder (vault generation marks in `vault-marks.json`, hosts this device confirmed in `known_hosts.confirmed`) is not part of the synced data folder: `<OS local data dir>/fernjo-device` (`%LOCALAPPDATA%\fernjo-device` on Windows), or `<FERNJO_DATA_DIR>/.device` for scratch runs; it is created on the first save, and `choose_data_folder` refuses a folder that contains it or lies inside it with `folder_device_dir`. A deterministic sample tree for filter and restart checks: `cargo run -p fernjo-core --example generate_tree -- <dir> 500`, then `FERNJO_DATA_DIR=<dir> pnpm tauri dev`. Format and load rules: `Docs/DECISIONS.md` ("`connections.json`: format, location, write strategy").
- Data safety (M7): `Store` (`crates/fernjo-core/src/store.rs`) keeps a SHA-256 fingerprint (`persist::Fingerprint`) of the bytes of `connections.json` it last read or wrote (taken from the bytes `persist::load` parsed, `Loaded.fingerprint`, never from a second read), and `mutate`, `replace_tree` and `clear_credential` compare it before every save; a file that changed on disk (sync tool, another device) is refused with `changed_on_disk`, a missing file is recreated. It is a check-then-write, not a lock (a sync tool can still win the race between check and rename), the same idea as the vault save guard. `Store::reload` re-reads the file and adopts it (nothing changes on an error); `commands::reload_tree` (read-only, so also allowed while a data folder change waits for a restart; counts in the three-places rule) serves it and maps an unreadable file to `reload_failed`, not the startup `load_failed`. UI: `TreeStore.changedOnDisk` is set when a command fails with `changed_on_disk` and `TreeStore.reload()` clears it; `NoticeBar.svelte` shows the bar with a Reload button, and a failed reload keeps the old tree, the flag and the normal error bar. The bar also shows (through `TreeStore.markChangedOnDisk()`) for a vault `delete_credential` (`VaultManager.svelte`) and for an import restore of a backup (`ImportDialog.svelte`, `apply_backup`), in addition to the plain error text; for both the error can stem from `vault.fernjo` (the restore runs `replace_entries` first) while the bar names `connections.json`, a known wording limit; a `changed_on_disk` from every other vault command, from a connections import and from export keeps its normal error text. Details: `Docs/DECISIONS.md` "M7: connections.json fingerprint check".
- Capped reads (M7): every read of `connections.json`, `settings.json` and their `.bak` copies goes through `persist::read_capped` (a thin wrapper over `fernjo_fs::read_capped`) with `fernjo_core::MAX_DATA_FILE_LEN` (64 MiB; the length is checked before reading and the read itself is bounded); a larger file is treated as unreadable by the existing unreadable-file rules. The vault has its own cap, `fernjo_vault::MAX_FILE_LEN`. A new reader of a data-folder file must use the capped helper, `fernjo_fs::read_capped` with the file's cap (the exceptions are listed in the "Hardened atomic writes" paragraph).
- JSON is never read through a `serde_json::Value` (M11 review #28; a `Value` costs about 98 bytes per input byte): a reader first runs `fernjo_core::json::head` (validates the whole document exactly as a `Value` parse would and returns only the named top-level fields, such as the schema version), then deserialises the same bytes into typed structs, borrowing a nested document as `&RawValue` (`persist::parse_document_bytes` for a `connections.json` document). A type that serde would buffer as `Content` (internally tagged enum, `#[serde(flatten)]`) gets a hand-written `Deserialize`, as `Node`, `RdpResolution` and the vault's `Secret` have. The peak memory is pinned by the `tests/memory.rs` binaries of `fernjo-core`, `fernjo-import` and `fernjo-sync` (counting allocator). Details: `Docs/DECISIONS.md` "M11 JSON files: never read through a `serde_json::Value`".
- `tauri_plugin_single_instance::init` must stay the first `.plugin(...)` call in `src-tauri/src/lib.rs` (a second launch has to be intercepted before any other plugin initialises; note that `AppState::open_for_app` runs while the builder is assembled, so a second launch also opens the data before it exits; besides reading the data files it reads the keychain for auto-unlock, which never deletes the item, and, on macOS, may trigger a keychain prompt).
- Navigation guard: `src-tauri/src/nav_guard.rs` (`is_app_url`, plugin `nav_guard::plugin()` registered right after the single-instance plugin in `lib.rs`) refuses every top-level navigation of the main webview that is not the platform's own app origin: `tauri://localhost` on macOS and Linux, `http(s)://tauri.localhost` on Windows and Android (`is_release_origin_for` takes the platform so the unit tests cover both sets on every OS), plus exactly the `build.devUrl` origin in a dev build. Terminal links do not navigate: `open_external_url` opens them in Rust and is independent of the guard. Residual limit (WebView2): a cancelled top-level GET navigation (`location.href`, link click) still sends one blind GET whose response is discarded. Details: `Docs/DECISIONS.md` "Webview hardening from day one".
- Vault state: `AppState.vault` is `VaultState::None` (no `vault.fernjo`), `Open(Vault)` (usable; "locked" is `!vault.is_unlocked()`, there is no separate Locked variant) or `Unusable` (file present but unreadable or from a newer version; never overwritten). `AppState::vault_status()` is the single reader. The `autoUnlock` flag in the status comes from `AppState.auto_unlock_known` (a per-vault cache kept by remember, set-auto-unlock, create and the startup auto-unlock), so lock and status call `KeyStore::get` only while the item's state is unknown (no cache entry for this vault yet; a failed get is not cached, so it is asked again on the next status); `vault_lock` also drops a decrypted import or backup from `AppState.pending` (`import_commands::clear_secret_pending`). `AppState.auto_unlock_issue` (set from the startup auto-unlock, cleared by a successful unlock or a new vault) is reported as `autoUnlockIssue` in `vault_status` (`key_not_accepted`, `keychain_unavailable`, `unavailable`, `rolled_back`; the stored key is never deleted and the UI shows a note); `AppState.generations` (`Arc<dyn GenerationStore>`: `FileGenerationStore` in `device_dir`, memory without one; tests get memory, `open_with_stores` shares one across a "restart") is attached to the vault before the startup auto-unlock and to a newly created vault; `AppState::open` is the test constructor (in-memory key store, `KdfParams::TEST`, no `settings.json`); `AppState::open_for_app` is the production one (`OsKeyStore`, default KDF cost) and is used by the real app even with `FERNJO_DATA_DIR` set, so a manual run with "Unlock automatically on this device" ticked writes a real Credential Manager/Keychain/Secret Service item (untick it, or delete the `fernjo` item, afterwards).
- `FERNJO_DATA_DIR` also disables `settings.json` (neither read nor written) and the data-folder dialog's Choose button; use it for every manual run. To test the data-folder dialog itself, run once without it and with `XDG_CONFIG_HOME` / `HOME` pointed at a scratch folder (Linux/macOS). On Windows overriding `APPDATA` does not work (the `directories` crate asks the Known Folder API), so the run uses the real `%APPDATA%\fernjo`; do it only on a machine where writing `settings.json` there is acceptable and delete it afterwards. `AppState.settings_unusable` (unreadable or newer-schema `settings.json`: never saved over) and `AppState.pending_data_dir` (folder chosen while a restart is pending, plus the data files that already existed there) belong to that mechanism; format and precedence in `Docs/DECISIONS.md` ("`settings.json` and data folder precedence").
- No-secret guard: the test `no_response_contains_a_secret` in `src-tauri/src/vault_commands.rs` runs every entry of its `table()` with sentinel secrets and asserts that no sentinel appears in any response, error, `Debug` output or `connections.json` (reveal, `sync_pairing_code` and `clipboard_read_text` return the secret by design; the guard has a narrow branch for `clipboard_read_text`: its response must contain the sentinel clipboard text and no other sentinel). `command_table_covers_every_tauri_command` is the count guard next to it. Adding a `#[tauri::command]` (also the `#[tauri::command(async)]` form) means updating three places: the function plus its `handlers` wrapper in `commands.rs`, `vault_commands.rs` or `data_folder.rs`, its entry in the test's `table()` (or `APP_HANDLE_EXEMPT` with a reason when it needs an `AppHandle`), and the `generate_handler!` list in `lib.rs`; the count guard compares them and fails if one is missing. A new source file with commands must also be added to the test's `sources` (`include_str!`). `table()` may also call plain functions that are deliberately not commands (`NOT_A_COMMAND`, currently `apply_data_folder`, `import_begin`, `export_connections_to` and `export_backup_to`, which take a path and so must never be reachable from the webview); the count guard asserts they are not registered. Commands that run an Argon2 derivation (`vault_create`, `vault_unlock`, `vault_unlock_older`, `vault_change_password`, `import_inspect`) are `#[tauri::command(async)]` so they do not block the main thread; `export_backup` (Argon2 too, plus the save dialog) and `import_apply` (many writes, no Argon2) are plain `#[tauri::command]`s on `async fn`s that move the work into `spawn_blocking` and take the state from their `AppHandle` (`app.state::<AppState>()`); `import_apply` still has its `table()` entry through its plain function.
- Vault save guard: `Vault::save` refuses with `changed_on_disk` when `vault.fernjo` no longer starts with the header this handle last read or wrote (another device or a sync tool changed it); a missing file is recreated. It is a check-then-write, not a lock. Lock and unlock to load the other version. Rollback protection: the body carries `generation` (v1 files read as 0, the header version stays 1; golden fixture `crates/fernjo-vault/tests/fixtures/v1-no-generation.fernjo` must keep opening), every save writes `max(generation, floor) + 1`, and `unlock`/`unlock_with_key` refuse a lower generation than the device mark (`vault-marks.json` in the device folder) as `rolled_back` only after the password or key proved genuine; `vault_unlock_older` (`unlock_accepting_older`) opens it anyway and re-stamps at once; auto-unlock never accepts. Details: `Docs/vault-format.md`, `Docs/DECISIONS.md` ("Vault: rollback protection"). Every read of the vault file goes through `read_capped` with `fernjo_vault::MAX_FILE_LEN` (64 MiB); a larger file is `unreadable`, so the vault is `Unusable` and untouched. Details: `Docs/vault-format.md`.
- Hardened atomic writes and KDF cap (M7, M11): the one atomic writer is `fernjo_fs::write_atomic` and the one capped reader `fernjo_fs::read_capped` (`crates/fernjo-fs`); every writer goes through `write_atomic` (core `persist`, the vault, `known_hosts`, which keeps its in-process `WRITE_LOCK`, the RDP pin file, the sync state files, the hub store and its `config.json`, `app_menu.rs`, `open_tabs.rs`, and the data-folder change's copy in `data_folder.rs`, `copy_atomic`, which reads its source through `read_capped` and has no fixed temp name since M11 review #80), so a fix lands once. The readers on `read_capped` are core `persist`, the vault's `format.rs`, the RDP pin file, the sync state files, `open_tabs.rs`, `data_folder.rs` `copy_atomic` and `KnownHosts::read` (`known_hosts` and `known_hosts.confirmed`, cap `MAX_KNOWN_HOSTS_LEN`, 16 MiB; its file I/O runs on tokio's blocking pool), plus `app_menu::should_offer` for the user's own `.desktop` entry (`MAX_ENTRY_LEN`, 64 KiB; any read failure means "offer again", except an entry that is a symbolic link, which the user manages and is never offered). The hub store reads `head.env` through `read_capped` with `MAX_ENVELOPE_LEN` (64 MiB, M11 review #49); the hub's `config.json` read and HTTP body reader in `server.rs` have their own bounds. Neither helper follows a symlink at the target name (M11 review #21): `read_capped` and the `.bak` copy open only a regular file (`open_regular`, public, also used by the vault's header check `check_unchanged_on_disk`: `symlink_metadata` everywhere, `O_NOFOLLOW | O_NONBLOCK` on Unix, then the handle's type), and `write_atomic` refuses a target that exists and is not a regular file (symlink, folder, FIFO) with "not a regular file …" (an `Other` error, never `InvalidData`, which the callers reserve for oversize, never `NotFound`) instead of following or replacing it; a deliberately symlinked single data file therefore fails, a symlinked folder above it works. `write_atomic` writes the bytes exactly to a random `<file>.<16 hex>.tmp` opened with `create_new` (mode 0600 on Unix for `FileMode::OwnerOnly`; never a fixed name that a planted symlink could redirect), syncs it, optionally keeps the `.bak`, renames, and fsyncs the directory on Unix (best effort); every failure removes its temp files; the temp files a cut-off save leaves behind are removed by `fernjo_fs::sweep_stale_temps` (exact `<file>.<16 hex>.tmp` regular files older than `STALE_TEMP_AGE`, a day; best effort) from `Store::open`, `settings::load`, `Vault::open` and the `KnownHosts` and `CertStore` writes. `WriteOptions` says what differs per caller: `Parent::{MustExist, CreatePrivate, CreateDefault}` (missing folders: none, 0700 on Unix, default mode; an existing folder's mode is never changed), `backup`, and `FileMode`; `WriteOptions::data_file()` is the common case. The `.bak` name is never opened for writing: the current file is copied into a second fresh temp file that is renamed onto `<file>.bak`, so a symlink planted there is replaced, not followed. The vault header's KDF cost is capped at 4x the default (`MAX_MEMORY_KIB`, `MAX_ITERATIONS`, `MAX_PARALLELISM` in `crates/fernjo-vault/src/format.rs`, shared by `Header::parse` and `validate`): a file or backup above it is `unreadable` naming the field, so a hostile file cannot make an unlock attempt run for many seconds; `change_password` raises a weaker stored cost to the default and never lowers one. The Windows keychain item uses `Local` persistence (no credential roaming). The Unix-only tests (file and folder modes, symlinks at the temp, `.bak` and target names, FIFOs) run in CI on Linux, not on Windows. Details: `Docs/DECISIONS.md` "M7: vault Low findings triage", "M7: SSH Low findings triage" and "M11: one set of hardened file helpers (`fernjo-fs`)".
- Credential updates: `CredentialUpdate` with a new `privateKey` and no `passphrase` keeps the stored passphrase; `passphrase` replaces it and `clearPassphrase: true` removes it (the UI sends it only from the "Remove stored passphrase" checkbox, never together with a typed passphrase).
- Tauri commands are plain functions over `AppState` in `src-tauri/src/commands.rs` (unit-tested without Tauri) with thin `#[tauri::command]` wrappers in `commands::handlers`; every mutating command returns the full snapshot. The UI (`ui/src/lib/store.svelte.ts`) keeps only view state and never derives validity or inherited values.
- Checking the UI in the real app on Windows without touching the user's mouse or keyboard (**security warning:** the debugging port is unauthenticated and, although it binds to 127.0.0.1, any process of another OS account on the machine can connect and call every Tauri command, among them `clipboard_read_text` and, with a real unlocked vault, `reveal_credential` and `sync_pairing_code`; use the recipe only on a single-user machine, only with a scratch `FERNJO_DATA_DIR` and no real vault or sync group, never with the owner's real data, and stop the app afterwards): start the app with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` (plus `FERNJO_DATA_DIR`), then talk to `http://127.0.0.1:9222/json` over the Chrome DevTools Protocol (Node 22+ has a global `WebSocket`): `Runtime.evaluate` for DOM and layout measurements, `Input.dispatchMouseEvent`/`dispatchKeyEvent` for browser-level input with real hit-testing, `Page.captureScreenshot`, `Emulation.setEmulatedMedia` for light/dark, console and network events. Scroll a row into view before clicking it (a row hidden under the properties panel swallows nothing and the click lands on the panel). Do not use `SendKeys`, `SetCursorPos` or `mouse_event` on the user's desktop. Gotchas: the dev server does not apply the CSP (check it in a `pnpm tauri build --no-bundle` binary, `target/release/fernjo.exe`, page URL `http://tauri.localhost/`), code run through DevTools is not bound by the page's CSP (`eval` tests prove nothing), and a forced `Stop-Process` can lose not-yet-flushed `localStorage` (close the window instead when testing persistence of view state). The recipe needs the WebView2 runtime files installed: a machine that only has the runtime's registry entry (as the development VM had after the move to a new device) cannot start the app, so neither `pnpm tauri dev`, `pnpm tauri build --no-bundle` nor this recipe works there; reinstall the Evergreen runtime (`winget install Microsoft.EdgeWebView2Runtime`) first. UI states that were only checked in a Chromium harness with a mocked API say so in their evidence. The window configuration in `src-tauri/tauri.conf.json` sets `additionalBrowserArgs` to wry's default (`--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection`) plus `--disable-component-update`, which stops the runtime's component updater from contacting `edge.microsoft.com` about a minute after start; setting the key replaces wry's default, so the default part is repeated, and the test `webview2_arguments_keep_wry_defaults_and_turn_off_the_component_updater` in `src-tauri/tests/tauri_conf.rs` pins both parts. `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` (the DevTools port) adds to the configured arguments. The switch is a Chromium one that the runtime honours, not on Microsoft's documented list: re-measure after a major runtime update. Details: `Docs/DECISIONS.md` "M7: WebView2 background connection".
- Session manager (M4) lives in `src-tauri/`: `sessions.rs` (the manager, one `Entry` per tab session, prompts, output forwarder; the wire contract is the doc comment at the top of that file, rationale in `Docs/DECISIONS.md` "M4 session IPC"), `session_flow.rs` (ack-based flow control), `session_commands.rs` (the `#[tauri::command]` wrappers; they count in the three-places rule above) and `connect_plan.rs` (resolves a node plus vault into a `ConnectPlan` synchronously, so the connect task needs no `AppState`). `SessionManager::close_all` runs on every main-window page load (`on_page_load` in `lib.rs`), so a reload or a crashed page never leaves sessions running without a UI. The SSH client itself is `crates/fernjo-ssh` (no Tauri). The known hosts file is `<data folder>/known_hosts`. A key found there is trusted silently only when this device confirmed it too: `ConnectParams.confirmed_hosts` is `<device_dir>/known_hosts.confirmed` (`sessions.rs` sets it from `AppState.device_dir`; without a device folder `confirmed_in_memory`, a `KnownHosts::in_memory()` held by the `SessionManager`, keeps the answers for the run; `None` for both disables the layer, as the SSH integration tests do). Otherwise the handshake stops before authentication with `PromptView::HostKeySynced` (UI `HostKeySyncedPrompt.svelte`, answered with `PromptAnswer::HostKey`); no seeding, so every host asks once per device. The confirmed file outranks `known_hosts` (M11): its key types are offered first, and a key that differs from any key this device confirmed for the host (whatever its type, also when `known_hosts` lost the host) gets the changed-key prompt with the confirmed fingerprints, never the first-contact or synced one; the very key this device confirmed is accepted silently even when `known_hosts` lost the host, and written back there after the handshake (`TrustAction::Restore`; best effort: a failed write is ignored and the connect goes on, while a failed write after a user's "Trust always" or "Replace" still stops it). Design: `Docs/DECISIONS.md` "M6 security fixes: hosts confirmed on this device". `fernjo_ssh::validate_host` (an allow-list: DNS-style names, IPv4, bracket-less IPv6 with optional `%zone`, at most 255 bytes) runs inside `host_port`, so every `KnownHosts` call, `Session::connect` and `connect_plan::resolve` refuse other hosts with `invalid_host`; a new code path that builds a `known_hosts` name must go through `host_port`.
- Session end and closing (M7): the `disconnected` state event carries `exitStatus` (the shell's exit code, when the server sent one) and `endedCleanly` (wire contract in the doc comment at the top of `sessions.rs`). Rust owns the verdict: `classify_end` says clean only for exit status 0 on a session that was connected for at least `MIN_AUTO_CLOSE_SESSION` (5 s), so a failed login or a quick error never closes unread; a non-zero status, a lost connection or an error keeps the tab with Reconnect. The UI owns the preference: `SessionStore` (`ui/src/lib/sessions.svelte.ts`) closes the tab on `endedCleanly` when `closeOnExit` is on; the setting lives in `TerminalPrefs` (`close_on_exit`, default on) in `settings.json` and is the "Close the tab when the shell exits" checkbox in Settings. The terminal settings input is the whole record, so **every `setTerminalSettings` call from the UI must send the stored `closeOnExit`** (an omitted field resets a stored `false` to true); `TerminalSettingsStore.save` requires it. The close confirmation is `on_window_event` in `lib.rs`: on `CloseRequested` of the main window with `SessionManager::connected_count()` above zero (only `Phase::Connected`; connecting and disconnected tabs do not count) it calls `prevent_close`, shows one non-blocking native dialog "Close fernjo?" ("Close" / "Keep open"; `AppState.close_prompt_open` keeps repeated clicks to one dialog) and, on "Close", runs `SessionManager::close_all` and `Window::destroy` (which does not raise `CloseRequested` again). The macOS Cmd+Q path (`RunEvent::ExitRequested`) asks the same way since M10: the pure `exit_action(code, connected, prompt_open)` in `sessions.rs` returns `Allow` (an explicit exit code, or nothing connected), `Prevent` (dialog already open) or `Ask`, and `ask_to_close` in `lib.rs` is the one dialog function both paths call (one `close_prompt_open` flag; the window destruction after "Close" raises `ExitRequested` without a code and is allowed, so there is no loop). Since M11 `restart_app` ("Restart now" after a data folder change) asks the same way: it takes the `Window`, decides with `SessionManager::restart_action`, calls `ask_to_close(window, connected, CloseThen::Restart)` ("Restart fernjo?", texts from `sessions::close_prompt`) and restarts through `sync_runner::finish_after_push` and `AppHandle::request_restart`, whose `ExitRequested` carries an exit code. There is no sync push before this restart: "Restart now" exists only while a data folder change waits, and sync is paused then (`sync_runner::ready` is false), so `finish_after_push` restarts at once (a push into a folder that is about to be swapped is not wanted). Never call `AppHandle::restart` directly (it skips the dialog). **Rules that must not be broken**
- **Secrets stay in Rust.** Passwords, private keys, passphrases, the sync hub secret and the sync key are never sent to the webview (only IDs and names), never written to `connections.json`, logs or webview storage. Secrets in memory use `secrecy`/`zeroize`.

- Files in the data folder are written atomically (temp file + rename) and keep a `.bak`.

**CI and repo**

## Maintaining the roadmap

The source of truth is `Docs/roadmap.json` (schema: `Docs/roadmap.schema.json`). `Docs/ROADMAP.md` is generated from it and never edited by hand. The .NET 10 SDK is required, even if the project otherwise uses a different stack.

1. Edit only `Docs/roadmap.json`: status, plan link, tick off tasks and criteria (`"done": true`, proof in `"evidence"`), scope changes, backlog. Omit optional fields, never set them to `null`.
2. Then run `dotnet run tools/roadmap.cs -- generate` and commit both files. Errors name the path in the JSON (for example `subprojects[0].milestones[2].completedOn`).
3. `dotnet run tools/roadmap.cs -- check` validates the schema, references and whether `ROADMAP.md` is up to date; CI (job `roadmap`) does the same.
4. Rules: `status` is `open`, `planned`, `in-progress` or `done`; `done` requires `completedOn` (YYYY-MM-DD), from `planned` on `plan` is required (path relative to `Docs/`); milestone ids are unique strings (`"5.1"` is allowed); prerequisites and `afterMilestone` must exist; title, goal and name stay on one line; texts are Markdown; anything that fits nowhere else goes into an entry in `blocks` (`title`, `text`).
5. A new milestone is an entry in `subprojects[].milestones`:

```json
{
  "id": "1", "title": "<Title>", "status": "open",
  "prerequisites": ["0"],
  "goal": "<One sentence: What becomes possible after this milestone?>",
  "tasks": [ { "text": "…", "done": false } ],
  "acceptance": [ { "text": "… (verifiable: test, command or a concrete manual check)", "done": false } ]
}
```

   A new subproject is an entry in `subprojects` (`number`, `name`, `spec` with `text` and/or `link`, `milestones`), a release is an entry in `releases` (`version`, `title`, `status`, `afterMilestone`, optionally `covers`, `date`, `intro`, `acceptance`, `blocks`).
6. Ideas belong in `backlog` (`title`, `text`, optionally `idea`). The skill `/ideen` (from `benjo-code/Labjo`) enters adopted ideas there and regenerates `Docs/ROADMAP.md`.

## Milestone workflow

Every change "in the roadmap" (linking a plan, setting status, ticking off tasks, scope changes) is a change to `Docs/roadmap.json` plus a regenerated `Docs/ROADMAP.md`, see "Maintaining the roadmap".

**"Plan milestone N":**
1. Create branch `feature/mNN-<topic>` from the current `dev`. Plan, roadmap maintenance and implementation of the milestone all go through this branch.
2. Read `Docs/ROADMAP.md`, the subproject's spec and the current state of the code.
3. Review the project's open ideas with `/ideen` (skill from `benjo-code/Labjo`, installation: `bash tools/install-ideen-skill.sh` there): adopt, implement or discard them. Whatever belongs in the milestone flows into the plan. The roadmap change lives on the milestone branch (when asked, choose "current branch").
4. If the milestone starts with "Create spec" or the subproject has no spec yet: first develop the spec through brainstorming with the user and store it under `Docs/superpowers/specs/`.
5. Write the plan to `Docs/superpowers/plans/YYYY-MM-DD-milestone-NN-<topic>.md`. The plan covers exactly the milestone's tasks and acceptance criteria, nothing more.
6. In the roadmap, link the plan and set the status to `🟡 planned` (overview table and milestone).

**Implementation:**
- Status `🔵 in progress`. Tick off every finished task in the roadmap immediately.
- Tick off acceptance criteria only once they have actually been verified, and note the proof behind them (test name, command + result, or manual check).
- At the end, status `✅ done` with date in table and milestone, then PR to `dev` (see "Git & branches").
- Record scope changes in the roadmap under "Scope changes", not silently in the code.
- Work only within the scope of the active milestone. Do not anticipate features, packages or architecture decisions of later milestones.

## Git & branches

- `main` holds only published states (releases). `dev` is the integration branch.
- Always work on `feature/<topic>` or `fix/<topic>`, branched from the current `dev` (`git switch dev && git pull && git switch -c feature/<topic>`).
- Before any work, check `git status` and the current branch. If on `main` or `dev`, create a feature branch first. Never commit directly to `main` or `dev`.
- Feature and fix branches go to `dev` via PR. Claude merges these PRs itself once the work is done and all CI checks are green (squash merge allowed).
- **Dependabot PRs are never merged by Claude**: the owner reviews and merges them (M11 review #32; this replaces required reviews on `dev`, which a single-maintainer repo cannot use, see `Docs/DECISIONS.md` "M11: owner decisions on the security review (2026-11-25)"). Claude may look at one and report, nothing more.
- PRs to `main` exist only for releases and hotfixes, and only on the user's explicit instruction.
- PRs between `main` and `dev` (release, hotfix, back-merge `main` → `dev`) are always merged with **"Create a merge commit"**, never squash or rebase. Otherwise `main` and `dev` lose their common history, and every release causes conflicts.
- Hotfix: branch `hotfix/<topic>` from `main` → PR to `main` → release (see below) → then merge `main` into `dev` via PR.
- Stage selectively (`git add <file>`). No `git add .` or `git add -A` when foreign changes that do not belong to the task are in the working tree. For files that were already modified beforehand, read `git diff <file>` first and use `git add -p` if needed.
- After every commit, check `git show --stat HEAD` against the expected file list.
- Commit messages follow Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`, `ci:`, optionally with a scope (`feat(api): …`).
- Forbidden without explicit instruction: force push, `git reset --hard`, deleting branches, rewriting history, bypassing hooks with `--no-verify`.
- Always create new repos (including companion ones such as `-Releases` or `-Privacy`) in the `benjo-code` organization, always with the owner spelled out (`gh repo create benjo-code/<name> …`), never under the personal account. Then verify with `gh repo view benjo-code/<name>`.

## Releases

- Versioning according to SemVer (`vMAJOR.MINOR.PATCH`).
- `CHANGELOG.md` → `[Unreleased]` is updated in every PR with a notable user-facing change (not for pure planning, roadmap or internal cleanup PRs).
- Every release is preceded by its own gate milestone in the roadmap (security check and release readiness: threat model update, independent review per changed area, `/security-review`, dependency checks, findings triaged in `Docs/release-checklist.md`, open owner checks listed, go or no-go verdict; owner decision 2026-11-26). The gate prepares the release and does not perform it. Not every milestone is a release: a release covers one or more milestones and ends with its gate.
- Procedure (only on instruction):
  1. Branch `release/vX.Y.Z` from `dev`, turn `[Unreleased]` in `CHANGELOG.md` into `[X.Y.Z] – YYYY-MM-DD` (naming the milestones it contains) and add a new, empty `[Unreleased]` above it; bump the hub image tag in `crates/fernjo-hub/deploy/compose.yaml` and `fernjo-hub.container` to the same version (together with `Cargo.toml` and `package.json`; `check-release-version.sh` fails the build otherwise).
  2. PR `release/vX.Y.Z` → `main` (merge commit).
  3. Tag, then a draft release (releases are immutable once published, so `release.yml` attaches the installers to the draft and publishes it): `git fetch origin main && git tag vX.Y.Z origin/main && git push origin vX.Y.Z` (the tag push starts `release.yml`), right after it `gh release create vX.Y.Z --draft --verify-tag --title "vX.Y.Z" --notes "<CHANGELOG section>"`. Do not publish the draft by hand: a published release takes no installers. If the run fails, fix the cause and repeat it while the release is still a draft: `gh run rerun <run id> --failed` (reuses the built installers), or, once the artifacts have expired or the fix needs a new build, `gh workflow run release.yml --ref vX.Y.Z`. A wrong tag cannot be moved or deleted (`v*` ruleset); the owner would have to switch the ruleset off.
  4. Merge `main` back into `dev` via PR (merge commit) so the two do not diverge.
